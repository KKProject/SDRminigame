## Context

管理页面当前由 `services/backend/src/admin-page.js` 返回一段包含样式和脚本的完整 HTML 字符串，Node HTTP server 同时负责业务 API 与前端页面。生产部署只同步 `services/backend`，Nginx 将所有请求反代到本机 8080。现有管理 API 已按 `/api/admin/*` 独立成形，因此前端可以在不改接口路径的前提下拆出。

当前管理员初始化在源码中固定用户名和密码，并在页面、示例配置、规范和测试中重复出现。管理员集合为空时需要保留可运维的首次初始化路径，但凭据必须由仓库外的受保护配置提供，且不得出现在日志或构建产物中。

## Goals / Non-Goals

**Goals:**

- 建立位于 `services/admin-web` 的独立 Vue 3 + Vite + TypeScript 管理端。
- 在 `/admin/` 保持稳定的生产入口，并保持 `/api/admin/*` 的接口兼容性。
- 改善信息层级、危险操作确认、异步反馈、响应式布局和无障碍体验。
- 让管理端拥有独立的构建、单元测试和部署边界。
- 删除所有可用的硬编码默认管理员凭据，使用环境变量完成一次性初始化。
- 提供不中断现有管理员登录能力的迁移和回滚路径。

**Non-Goals:**

- 不新增玩家、牌局详情、日志分析或实时监控等后端业务能力。
- 不改变现有管理 API 的路径、请求字段和主要响应结构。
- 不在本次变更中将 bearer token 会话迁移为 HttpOnly Cookie。
- 不修改小游戏客户端或 WebSocket 协议。
- 不引入多租户或比 `admin`、`superadmin` 更细粒度的权限模型。

## Decisions

### 1. 管理端作为独立 Vue 应用

在 `services/backend` 同级创建 `services/admin-web`，采用 Vue 3 Composition API、Vite、TypeScript、Vue Router 和 Pinia。UI 使用 Element Plus 提供表单、表格、对话框和反馈组件，并通过项目级 design tokens 覆盖视觉风格。

选择该组合是因为管理端具有明确的路由、会话状态和表格表单需求，成熟组件可以减少自制交互控件的无障碍与状态缺陷。相比继续扩展原生脚本，组件化和类型约束更利于长期维护；相比把 Vue 构建产物复制进 backend 源码，独立目录能保持清晰的依赖和部署边界。

### 2. 采用浅色工作区配深色侧栏的信息架构

登录后使用固定深色侧栏、浅色内容区和铜橙色品牌强调色。一级路由分为“数据概览”和“管理员账号”，普通管理员不显示且不能进入管理员账号页面。集合计数使用概览卡片和数据表共同表达，等宽字体仅用于集合名与技术标识。

不采用首轮设计检索给出的横向滚动展示，因为它适合营销内容而非运维任务；也不默认使用纯 OLED 黑色主题，以保证日间长时间查看和高信息密度下的可读性。首期不实现主题切换，但颜色均以 CSS variables 管理，为后续暗色模式留出空间。

### 3. 危险操作统一使用可访问的确认对话框

清空集合、清空全部和禁用管理员都使用页面内对话框，不再调用 `window.prompt`。对话框展示目标、影响范围和不可逆提示，要求输入 API 规定的确认文本，提交期间禁止重复操作，成功后刷新相关数据，失败时保留上下文并提供重试。

该选择能改善移动端体验、键盘操作和错误反馈，同时不降低后端现有的白名单及确认文本校验。

### 4. 会话仍使用 bearer token，但缩小浏览器持久化范围

API client 继续在 `Authorization: Bearer` 中发送 token，以保持后端兼容。管理端集中封装请求、错误映射和 401 处理；token 默认保存在 `sessionStorage`，关闭标签页后失效。路由守卫调用 `/api/admin/me` 恢复身份，401 时清除本地会话并返回登录页。

HttpOnly Cookie 能进一步降低 token 被脚本读取的风险，但会同时涉及 CSRF、Cookie 属性、CORS 和后端会话协议，超出本次前端拆分的兼容目标，可作为后续安全变更。

### 5. Nginx 托管静态产物，Node 只保留 API

Vite 的 base 和 Vue Router history base 均设为 `/admin/`。生产构建产物同步到独立的版本化静态目录，Nginx 对 `/admin/` 使用 `try_files` 回退至 `index.html`，对 `/api/` 和 `/ws` 维持现有反向代理。`/admin` 永久重定向到 `/admin/`，保证相对资源和路由基址一致。

相比由 Node 读取 `dist`，Nginx 静态托管无需让后端部署携带前端产物，也能独立设置缓存：`index.html` 不缓存，带 hash 的 assets 长缓存。

### 6. 使用环境变量进行一次性初始超级管理员创建

新增 `INITIAL_ADMIN_USERNAME` 和 `INITIAL_ADMIN_PASSWORD` 配置。服务启动时：

1. 若 `adminUsers` 已存在任意管理员，不读取密码完成账号覆盖，也不重置任何管理员。
2. 若集合为空，则要求两个变量均存在并通过现有用户名、密码校验；合法时创建带 `defaultAdmin: true` 标记的 `superadmin`。
3. 若集合为空且配置缺失或非法，服务启动失败，错误只指出缺失或非法的变量名，不回显变量值。

初始化密码只进入 PBKDF2 哈希流程，不写入日志、响应、页面或前端环境变量。部署文档只说明设置方式，不提供示例可用密码。保留 `defaultAdmin` 保护语义，但不再假设固定用户名。

相比生成随机密码并打印日志，环境变量方案不会把凭据暴露到日志；相比每次启动强制同步环境变量，它也不会意外重置生产账号。

### 7. 分层验证管理端和后端契约

管理端使用 Vitest 与 Vue Test Utils 覆盖路由守卫、API 错误处理、角色可见性、表单校验和危险确认状态；生产构建作为部署前检查。后端回归继续覆盖所有管理 API，并新增空集合初始化、已有集合不覆盖、缺少配置拒绝启动及错误脱敏测试。公网冒烟检查验证 `/admin/` 返回 Vue 入口、静态资源可访问、`/healthz` 正常，且不执行真实登录或数据清理。

## Risks / Trade-offs

- [Nginx 配置与静态产物部署不同步会导致 `/admin/` 不可用] → 先上传并校验新产物，再原子切换静态目录软链接和校验 Nginx 配置。
- [history 路由刷新返回 404] → 为 `/admin/` 配置 `try_files ... /admin/index.html`，并加入直接访问子路由的冒烟测试。
- [首次部署缺少初始化变量导致后端无法启动] → 部署前只检查变量是否存在并脱敏输出状态；已有管理员数据时允许安全启动，不强制依赖初始化密码。
- [初始化账号判定与旧默认账号保护语义不一致] → 以数据库中的 `defaultAdmin` 标记作为保护依据，不再比较固定用户名。
- [sessionStorage 仍可被同源 XSS 读取] → 不渲染不可信 HTML、依赖构建锁定并保持 CSP 兼容；Cookie 会话另立变更处理。
- [引入 UI 组件库增加首屏体积] → 使用按需导入并检查生产构建体积，管理端不追求弱网小游戏级别的极限体积。
- [前后端独立部署产生版本短暂不一致] → 保持 API 向后兼容，部署流程先发布兼容后端，再发布前端；破坏性 API 变更不纳入本次范围。

## Migration Plan

1. 备份并确认生产 `adminUsers` 已存在管理员；已有管理员时不设置初始化密码，只有集合为空的首次部署或显式灾难恢复流程才临时配置初始化变量且不输出变量值。
2. 发布兼容新旧页面的后端安全初始化逻辑并运行后端回归，验证已有管理员未被覆盖。
3. 构建 `admin-web`，将带版本的产物同步到独立静态目录并校验文件完整性。
4. 更新并校验 Nginx 配置，切换 `/admin/` 至静态目录，同时保留 `/api/admin/*` 反代。
5. 验证登录、集合计数、权限可见性和只读冒烟；再移除后端 `admin-page.js` 与 HTML 路由并发布最终后端。
6. 更新部署脚本和运维说明，确保后续管理端、后端可以分别部署且完整流程可一键验证。

回滚时将 Nginx 静态目录软链接切回上一版本；若需要恢复内嵌页面，则同时回滚后端到包含 `admin-page.js` 的上一发布。回滚不得删除或重建 `adminUsers`，也不得改变现有密码摘要。

## Open Questions

- 生产静态根目录的最终绝对路径需在实现时读取现有 Nginx 配置后确定；部署脚本应允许通过环境变量覆盖，不能在未核对服务器布局时写死。
- 是否在后续单独变更中将 bearer token 改为 HttpOnly、Secure、SameSite Cookie 会话。
