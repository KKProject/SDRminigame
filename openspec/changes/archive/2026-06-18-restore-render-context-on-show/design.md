## Context

项目已经通过 `game.json` 请求横屏运行，并在 `js/render.js` 中维护稳定的横屏窗口指标。当前机制能防御启动首帧返回纵屏或异常尺寸，也能在真实窗口尺寸、安全区或像素比变化后重建 Canvas 和布局。

这次问题发生在小程序退出或微信分享后再进入：微信运行时会让小游戏经历横屏、微信竖屏界面、再回横屏的过程。项目本身是横屏游戏，如果中间任何模块按竖屏窗口宽高创建布局，就可能留下竖屏布局缓存或命中区域；回到同一组横屏指标时又会被普通重复通知忽略。渲染层还可能恢复或重建底层 Canvas/2D context，使旧 context transform 失效。

## Goals / Non-Goals

**Goals:**

- 前台恢复时重新应用当前稳定的 Canvas backing store 与 2D context transform。
- 无论运行时临时报告横屏还是竖屏窗口宽高，游戏内部正式逻辑坐标系都保持横屏。
- 保留普通重复窗口通知的幂等行为，避免重复重建布局、销毁菜单按钮或取消动画。
- 前台恢复后继续读取短时间窗口指标；若出现新的有效横屏指标或安全区变化，再沿用现有稳定确认与重布局流程。
- 自动检查覆盖“指标相同但需要恢复 Canvas/context”的前台恢复路径。

**Non-Goals:**

- 不实现纵屏布局。
- 不改变牌局状态、在线协议、好友房流程或服务端逻辑。
- 不在前台恢复时无条件重排手牌列或重启动动画。
- 不依赖具体设备型号、屏幕尺寸或微信版本判断。

## Decisions

### 1. 将运行时窗口指标归一为横屏逻辑坐标系

`createRenderMetrics()` 在读取窗口宽高后先归一化方向：逻辑宽度始终取较大值，逻辑高度始终取较小值。竖屏来源的 `safeArea` 不作为正式横屏安全区使用，避免把微信竖屏界面的刘海、顶部栏或底部手势区映射到横屏牌桌。

原因：小游戏已经通过配置声明横屏，游戏布局没有纵屏设计。把临时竖屏宽高转成横屏逻辑尺寸，可以保证菜单、牌桌、手牌、按钮和命中区域始终运行在同一套横屏坐标系里。这样即使分享面板中间让运行时短暂变成竖屏，游戏内部也不会创建正式竖屏布局。

### 2. 将前台恢复建模为独立渲染生命周期事件

`wx.onWindowResize` 继续表示窗口候选指标变化；`wx.onShow` 表示小程序前台恢复。主程序在 `onShow` 中触发专门的恢复路径，而不是只复用普通 resize 处理。

原因：前台恢复时尺寸可能完全不变，但 Canvas/context 仍可能被微信重置。把它当成普通重复尺寸会跳过最关键的上下文恢复。

备选方案是延长 `metricsRetryRemaining` 的帧数。该方案只能发现后续尺寸变化，无法处理指标始终相同但 context 被重置的场景。

### 3. 渲染指标管理器提供“重应用当前稳定指标”

`RenderMetricsManager` 增加类似 `restore()` 或 `reapplyStableMetrics()` 的入口：当已有稳定指标时，先重新解析当前 Canvas 与 2D context，再强制执行 `applyCanvasMetrics()` 与 `applyContextScale()`，并更新已应用签名。该入口不改变 `stableSignature`，不通知普通布局监听者，也不把它计为新候选提交。

原因：Canvas backing store、当前 2D context 对象和 context transform 都是渲染状态，布局监听者关心的是逻辑指标变化。分享返回后微信可能让 `getContext('2d')` 返回新的有效 context；相同指标恢复需要重新绑定当前 context，但不应触发完整重布局副作用。

### 4. 前台恢复后仍进行短时指标确认

`onShow` 在重应用当前稳定指标后，进入短暂恢复窗口：后续若干帧继续重应用当前稳定 Canvas/context，并同时读取窗口信息。如果微信先返回竖屏来源的窗口指标，管理器将其归一化为横屏逻辑尺寸；已有稳定横屏时不会提交竖屏来源的安全区，但会保持恢复最后稳定横屏上下文。如果连续确认到新的有效横屏指标签名，则提交并通知布局重建。

原因：微信分享会让小游戏经历横屏、微信竖屏 UI、再回横屏的过程，底层 Canvas/context 可能在 `onShow` 回调后仍被运行时继续改动。单次恢复不足以覆盖这个过渡窗口；持续短时恢复负责兜住迟到的 context 重置，稳定确认负责后续真实变化。

### 5. 普通重复通知保持完全幂等

`wx.onWindowResize` 或帧轮询读到与当前稳定指标相同的候选时，仍不得重复重置 Canvas、重建布局、销毁授权按钮或取消动画。只有已经观察到无效/竖屏过渡后，下一次相同稳定横屏指标才会发出一次强制布局刷新通知；前台恢复路径也可以在相同指标签名下重应用 Canvas/context。

原因：现有重复通知保护是正确的性能和动画保护，只是缺少“竖屏过渡后回到同一横屏”的恢复例外。这个例外负责清理可能基于竖屏状态残留的布局缓存和命中区域，但不把它当作真实尺寸变化来取消动画。

### 6. 动画边界按“指标是否变化”而不是“是否恢复”判断

前台恢复重应用相同指标时，动画管理器不得取消活动 Tween、重复音效或重复完成通知。只有稳定指标发生实际变化时，才沿用已有布局变化处理，取消旧坐标动画并按权威状态恢复。

原因：同尺寸恢复不改变逻辑坐标，取消动画会制造新的视觉跳变；真实尺寸变化才会让旧动画目标失效。

## Risks / Trade-offs

- [前台恢复窗口期重复设置 Canvas 宽高会清空当前帧] -> 恢复只在短时窗口内发生，并在每帧渲染前完成，随后由主循环重新绘制菜单或牌桌。
- [不通知布局监听者可能漏掉必须重建的原生按钮] -> 只有指标签名相同时不通知；如果安全区或按钮坐标变化，稳定确认会提交新指标并触发菜单重建。
- [部分微信版本 `onShow` 触发多次] -> 恢复入口必须幂等，重复重应用 Canvas/context 不得影响牌局状态或动画完成通知。
- [恢复期间短暂读到纵屏指标] -> 沿用现有无效候选过滤，保留最后稳定布局。

## Migration Plan

1. 在渲染指标管理器中增加重应用当前稳定 Canvas/context 的入口，并让它可测试。
2. 调整主程序生命周期，让 `wx.onShow` 走前台恢复路径，`wx.onWindowResize` 继续走普通窗口变化路径。
3. 保持稳定指标变化时的现有布局和动画恢复逻辑不变。
4. 扩展自动检查，模拟相同指标签名下 Canvas/context 被重置后通过前台恢复重新应用。
5. 在真机验证冷启动、切后台恢复、退出小程序再进入、横屏方向左右切换。
