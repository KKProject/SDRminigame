## Context

现有规则已经要求“后续从牌堆抓出的牌不进入手牌”，但禁吃禁胡逻辑仍使用宽泛的 discarded key 概念。实现里 action history 同时承载玩家手牌主动出牌、抓牌无人响应后的自动流走等事件，如果直接按 key 查询历史，会把非手牌事件误判为“玩家打过”。

这次变更的核心不是新增动作，而是收紧规则语义：只有开局发到手牌中的牌，被玩家在出牌阶段或操作后强制出牌阶段主动选择打掉，才会写入“手牌主动打出 key”记录。后续抓牌出现的牌不进入手牌，因此它的流走不可能形成这类记录。

## Goals / Non-Goals

**Goals:**

- 建立明确的 `manualHandDiscardKeys` 规则语义，只记录玩家从开局手牌集合主动打出的 key。
- 让 chi、hu、强制 chi 处罚都基于同一个记录语义。
- 服务端裁决、客户端按钮展示、测试用例使用一致口径。
- 确保被其他玩家响应拿走的出牌，仍然保留在原出牌玩家的手牌主动打出记录中。

**Non-Goals:**

- 不改变抓牌不进手牌的基础流程。
- 不改变一次只能打一张牌的基础规则。
- 不重新设计整套 action history 或回放协议。
- 不改变普通同花牌型出牌限制、胡牌门型、响应优先级或结算分值。

## Decisions

1. 以“事件来源”而不是“牌当前所在位置”定义打过记录。

   规则上“打过某 key”只来自玩家主动从手牌打出。即使这张牌随后被别人吃、碰、招、胡拿走，原玩家仍然打过该 key。相反，抓牌后无人响应进入弃牌堆，只是牌堆流转结果，不是玩家从手牌打出。

2. 服务端维护权威记录，客户端只做展示过滤。

   服务端在响应枚举和动作提交校验时必须使用权威的手牌主动打出记录。客户端可以使用同一规则提前隐藏按钮，但不能因为客户端没隐藏而允许非法动作通过。

3. 禁胡按同 key 全量禁止。

   旧规则只禁止 chi-style hu，即 appearing card 参与 `xy` 或 `xyz` 门的胡。新规则要求玩家从开局手牌主动打过某 key 后，本轮后续不能用同 key appearing card 胡牌，无论最终分解成 `xy`、`xyz`、`xx`、`xxx` 或高阶同张门。

4. 强制吃和已打过冲突时直接进圈。

   如果某张 appearing card 对玩家构成必须吃，但该 key 已在该玩家的手牌主动打出记录里，则不能展示可点的吃按钮，也不能当作普通过牌处理；服务端应判定该玩家进圈，并按现有 circle-loss 结算让其赔三家。

5. 历史兼容采用低风险策略。

   对正在进行的旧房间，不做复杂数据迁移。实现时可以继续识别既有手牌主动出牌事件类型，并显式排除抓牌自动流走事件；新房间和新回合从规则状态中写入清晰字段。若旧快照缺少足够来源信息，以不误伤玩家为优先，避免把抓牌流走误记为打过。

## Risks / Trade-offs

- [Risk] 客户端和服务端各有一份 evaluator，容易出现口径漂移。  
  Mitigation: 同时更新服务端与客户端 evaluator，并新增同名规则测试覆盖禁吃、禁胡、抓牌不污染记录和强制吃进圈。

- [Risk] 旧 action history 命名仍叫 discard，容易被后续维护者误用。  
  Mitigation: 引入语义更明确的 helper，例如 `hasManuallyDiscardedHandKey`，并让旧的宽泛 helper 不再用于响应限制。

- [Risk] 强制吃进圈需要接入响应窗口决策流程，不能只靠隐藏按钮完成。  
  Mitigation: 在服务端响应枚举或强制动作检测阶段识别“必须吃但已打过”状态，直接走现有 circle-loss 结果构建和事件广播。

- [Risk] 旧测试里“已打过同 key 仍可同张门胡”的断言会与新规则冲突。  
  Mitigation: 将该断言改为禁止 hu，并补充一个相反场景：非手牌抓牌流走同 key 后仍可正常吃/胡。
