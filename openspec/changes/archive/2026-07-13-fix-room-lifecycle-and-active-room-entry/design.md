## Context

当前服务端仅把 `closed` 视为非活动状态，`queryActiveRoom` 因此会返回 `waiting`、`playing`、`finished` 和 `tableResult`。客户端 `startLobby` 对所有返回结果统一执行 `enterExistingRoom`，于是最大局数结束后的 `tableResult` 也会在下次启动时自动进入游戏页。

创建房间使用同一查询结果做防重复校验，但当前以 `alreadyInRoom: true` 的成功形态返回旧房间；客户端收到后会静默调用 `enterExistingRoom`。此外，`leaveTable` 即使收到服务端 `ROOM_NOT_FINISHED`，也会清理本地会话并回大厅，形成“客户端看似已离房、服务端仍保留占用”的状态分裂。

房间状态的业务含义必须保持清晰：`finished` 是单局结算完成、但尚未达到房间最大局数，仍属于可继续房间；`tableResult` 才是最大局数后的终局状态。现有 15 秒终局重开流程仍服务于一直留在结果页的玩家，但不再把终局房间作为小游戏重新启动后的自动恢复目标。

## Goals / Non-Goals

**Goals:**

- 建立唯一的可恢复房间状态集合：`waiting`、`playing`、`finished`。
- 启动时按状态确定等待页、游戏页或大厅，不再恢复 `tableResult`。
- 玩家重新进入大厅后释放其终局房间占用，使旧房间不会阻塞新建房间。
- 进行中房间冲突以明确错误表达，客户端不得把创建操作静默改成进入旧房间。
- 只有服务端确认离房成功或房间已经终止时，客户端才清理本地房间会话。
- 用回归测试固定服务端状态分类和客户端页面路由。

**Non-Goals:**

- 不改变 `finished` 状态下普通下一局的开局、积分累计或座位保留规则。
- 不取消玩家持续停留在 `tableResult` 结果页时已有的 15 秒房主重开流程。
- 不允许同一玩家同时加入两张 `waiting`、`playing` 或 `finished` 房间。
- 不立即物理删除 MongoDB 中的终局/关闭房间文档；本 change 的“销毁”指关闭生命周期并释放玩家占用，历史数据清理由独立保留策略处理。

## Decisions

### 1. 用显式状态分类替代“非 closed 即活动”

服务端引入语义明确的状态判断：

- 可恢复/占用状态：`waiting`、`playing`、`finished`。
- 终局状态：`tableResult`。
- 已关闭状态：`closed`。

`activeRoom`、创建前防重复、分享加入冲突检查都使用同一分类函数，避免不同入口各自推断状态。选择白名单而不是继续维护 `CLOSED_ROOM_STATUSES` 黑名单，是为了让以后新增状态时默认不被错误当成可恢复房间。

### 2. 启动查询先归一化，再按状态返回页面目标

`activeRoom` 查询候选房间后先根据权威引擎调用现有结算状态同步，修复 `playing + phase=result` 的短暂漂移，再做页面分类：

| 服务端状态 | 启动落点 | 是否阻塞新建 |
| --- | --- | --- |
| `waiting` | 等待页面 | 是 |
| `playing` | 游戏页面 | 是 |
| `finished` | 游戏页面 | 是 |
| `tableResult` | 大厅 | 否 |
| `closed` / 不存在 | 大厅 | 否 |

客户端不再用“返回了 room 就统一进入牌桌”的宽泛逻辑，而是对状态进行穷举路由；未知状态按不可安全恢复处理，留在大厅并记录诊断信息。

### 3. 玩家重新进入大厅时释放其终局房间成员关系

当 `activeRoom` 或创建前检查发现玩家仍挂在 `tableResult` 房间时，服务端执行幂等的终局释放：从 `players/playerOpenids` 移除当前玩家；若玩家是房主、剩余真人不足最低开局人数或终局重开窗口已过期，则将房间标记为 `closed` 并清理公开状态。随后继续查找真正可恢复的房间。

这样既不会因为一名玩家重启就把仍满足条件的其他玩家全部强制清退，也不会让已回大厅的玩家继续计入重开同意人数。创建接口必须再次执行该清理，防止旧客户端跳过启动查询后直接创建。

备选方案是让 `activeRoom` 只忽略 `tableResult` 而不改成员关系，但这会留下重开人数、玩家占用和旧数据长期漂移，因此不采用。

### 4. 创建冲突改为明确失败，不再返回成功形态

若创建前发现 `waiting`、`playing` 或 `finished` 房间，服务端返回 `ok: false`、稳定错误码（例如 `ALREADY_IN_ACTIVE_ROOM`）以及最小已有房间摘要。客户端停留在创建页，显示“你已有进行中的房间，请先继续当前房间”，并提供返回大厅/继续当前房间的正常导航；不得在确认创建的回调里自动进入旧房间。

`activeRoom` 仍负责启动时自动恢复，因此正常启动不会让玩家先看到可创建入口。创建接口的冲突只是并发、旧页面或本地状态漂移情况下的最后一道保护。

### 5. 离桌以服务端结果为准

`leaveTable` 只有在服务端返回 `ok: true`、`closed`、`left` 或等价终止结果后，才调用统一的 `returnToLobby` 清理 socket、房间号、动画队列和输入状态。收到 `ROOM_NOT_FINISHED` 等拒绝时，客户端保留或重新拉取当前房间，并显示明确提示。

该决策消除本地“假离房”，使后续创建按钮的可见性与服务端占用一致。

### 6. 兼容旧房间数据并保持操作幂等

终局释放和关闭操作必须允许重复调用：玩家已经移除、房间已经关闭或公开状态已经不存在时仍返回稳定结果。旧文档缺少 `playerOpenids`、`rematch.deadlineAt` 等字段时，从 `players` 和现有 rematch 状态重建必要信息，不进行一次性数据库迁移。

## Risks / Trade-offs

- [Risk] `activeRoom` 从纯查询变为可执行终局成员释放。→ Mitigation：限制副作用只作用于调用者所属的 `tableResult`，实现幂等，并在服务端测试中覆盖重复调用。
- [Risk] 房主重启进入大厅会导致旧终局房间关闭，其他玩家失去重开机会。→ Mitigation：这是房主离开终局流程的明确语义；服务端广播关闭状态，其他客户端统一回大厅。
- [Risk] 创建请求与终局重开请求并发，可能让同一玩家短暂出现在两个流程。→ Mitigation：两条入口都重新读取最新房间状态；终局释放后从重开必需成员中移除该玩家，重开前再次校验当前成员。
- [Risk] 旧客户端仍把冲突响应解释成 `alreadyInRoom`。→ Mitigation：服务端使用明确失败码并保留可诊断摘要，新客户端先部署；后端不再以成功响应诱导静默跳转。
- [Risk] 未知的新房间状态被留在大厅。→ Mitigation：白名单默认保护玩家不进入无法解释的页面，同时记录状态，新增状态时必须同步扩展规格和路由。

## Migration Plan

1. 先实现服务端状态分类、终局成员释放以及 `activeRoom/createRoom` 的新响应语义，并补充 server core 回归。
2. 实现客户端启动状态路由、创建冲突提示和离桌结果校验，补充 online 回归。
3. 运行 `run-online-checks`、`run-server-core-checks`、后端测试与 OpenSpec 严格校验。
4. 先部署后端再上传小游戏，缩短新客户端遇到旧响应语义的窗口。
5. 若需要回滚，客户端恢复旧路由前先回滚服务端冲突响应；已标记 `closed` 或已释放成员的历史终局房间不回填。
