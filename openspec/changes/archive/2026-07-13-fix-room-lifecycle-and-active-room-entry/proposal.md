## Why

房间达到最终结果后仍被服务端视为玩家的“当前房间”，导致玩家再次启动小游戏时被拉回已结束牌桌；另一方面，玩家从进行中的房间回到大厅后进入创建页，确认创建时又会被静默送回旧房间，页面表现与服务端房间占用状态不一致。需要统一房间生命周期判定、启动路由和创建房间冲突反馈，让可恢复房间与已结束房间有明确边界。

## What Changes

- 明确启动大厅按房间状态路由：`waiting` 自动进入等待页面，`playing` 和 `finished` 自动进入游戏页面，`tableResult`、`closed` 或无房间时停留大厅并显示“创建房间”。
- 将 `tableResult` 从启动恢复和创建房间占用判定中排除；服务端在相关入口完成最终结果房间的关闭或释放处理，避免旧房间长期占用玩家。
- 保留 `finished` 作为“单局结束但房间总局数未完成”的可恢复状态，继续进入游戏页面并允许房主开启下一局。
- 玩家仍有 `waiting`、`playing` 或 `finished` 房间时，创建请求 MUST NOT 静默进入旧房间；服务端返回明确冲突，客户端提示玩家继续当前房间。
- 修正客户端本地回大厅与服务端离房结果不一致的问题：服务端拒绝离开进行中房间时，客户端不得假装已成功释放房间。
- 增加服务端房间生命周期、重复创建和客户端启动/创建路由回归测试。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `online-lobby`: 明确不同房间状态对应的启动页面、终局房间的大厅落点，以及创建房间冲突时的客户端行为。
- `online-matchmaking`: 调整未结束房间查询和重复创建判定，明确 `finished` 可恢复、`tableResult` 不再占用玩家的新房间创建资格。

## Impact

- 客户端：`js/net/online.js` 的启动查询、已有房间进入、创建房间和离桌流程，以及 `js/main.js` 的大厅/等待页/游戏页路由。
- 服务端：`services/backend/src/game/room.js` 的 `activeRoom`、`createRoom`、终局状态清理和离房结果处理。
- API 行为：当前房间查询与创建房间冲突响应的状态语义会变化；不新增外部依赖或数据库集合。
- 测试与规格：更新 online/server core 回归用例，并替换现有“最终结果房间始终可自动重连”的旧断言。
