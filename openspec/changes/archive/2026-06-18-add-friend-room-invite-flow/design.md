## Context

项目当前已经有在线大厅、创建好友房、加入好友房、主动查询未结束房间、服务端权威开局和空座 AI 补位能力。刚完成的大厅流程为了保持可玩，创建房间后仍沿用自测路径自动 `startRound`。这与真人好友对战的体验不匹配：房主需要先停在等待房间，邀请好友进入，同桌真人准备后再开局。

微信小游戏分享能力支持通过 `wx.shareAppMessage` 或 `wx.onShareAppMessage` 携带 `query`，从分享卡片进入后可通过 `wx.getLaunchOptionsSync()` 或 `wx.onShow()` 读取启动参数。这个 change 将使用 `roomId` 作为分享参数，让被邀请玩家登录后自动加入指定房间。

## Goals / Non-Goals

**Goals:**

- 创建房间后进入等待房间，不自动开局。
- 等待房间显示房间号、局数、真人玩家列表、准备状态、准备按钮和微信邀请按钮。
- 房主可通过微信邀请按钮主动分享房间；分享 query 携带 `roomId`。
- 被邀请玩家通过分享卡片进入时，登录后自动加入目标房间。
- 等待房间中玩家可准备；第一版开局条件为至少 2 名真人在房间内，且房主已准备。
- 开局时空座继续由服务端 AI 补位，保持当前服务端权威引擎和动画同步流程。
- 对房间不存在、已满、已开局、玩家已有其他未结束房间等情况给出明确状态。

**Non-Goals:**

- 不要求 4 名真人满座才开局。
- 不实现房间聊天、踢人、转让房主、换座、观战、邀请海报、群排行榜。
- 不实现房间过期清理或复杂断线等待策略。
- 不改变牌局内行牌规则、计分规则和动画同步协议。

## Decisions

### 1. 等待房间复用大厅画布 UI

客户端在创建房间或加入房间后仍保持菜单覆盖层 active，切换到 `room-waiting` 视图。进入正式牌桌后再隐藏菜单并启用牌桌触摸输入。

原因：现有 `StartMenu` 已经承载登录后大厅、局数选择、loading 和错误状态。等待房间是牌桌前流程，不需要引入新的页面系统。

备选方案是在牌桌渲染器中加等待房间场景，但它会把非牌局 UI 混入 `TableRenderer`，不利于保持服务端权威牌局渲染边界。

### 2. 服务端增加等待房间快照与准备动作

新增房间 action：

- `roomInfo`：返回等待房间公开信息，包括 `roomId`、`status`、`hostOpenid`、`settings`、`players`、`canStart`。
- `setReady`：设置当前玩家 ready 状态。
- `startRoom` 或扩展 `startRound`：校验开局条件后开局。

等待房间 `players` 条目保存：

```js
{
  seat,
  openid,
  nickName,
  avatarUrl,
  isHuman: true,
  online: true,
  ready: false,
  lastSeenAt
}
```

原因：等待房间不含手牌，不需要走 `pull` 的私密手牌模型；单独的公开快照更轻，也便于邀请者和被邀请者看到同一份玩家列表。

### 3. 第一版开局条件：至少 2 名真人且房主 ready

开局条件定为：

- 房间状态为 `waiting`。
- 当前调用者是房主。
- 房间内真人数至少 2。
- 房主 `ready === true`。

其他真人是否必须 ready 第一版不强制，但 UI 仍显示每位玩家的准备状态。开局后空座由现有 `buildSeatPlayers` 逻辑补 AI。

原因：这个条件能满足“邀请一个好友即可开始真人对战”的最小闭环，也保留后续升级到“所有真人准备后开局”的空间。

备选方案是所有真人必须准备后自动开局。它更严格，但在第一版里更容易让房主等待或卡住，尤其好友加入后还不熟悉准备按钮。

### 4. 分享参数只传 `roomId`

分享 query 使用简单键值格式：

```text
roomId=123456&source=friendInvite
```

客户端在启动时通过 `wx.getLaunchOptionsSync()` 读取一次，在回前台时通过 `wx.onShow()` 读取新参数。读到 `roomId` 后缓存为 pending invite，在线登录成功后优先尝试加入该房间。

原因：小游戏分享 query 能直接满足按房间号加入的需求。只传 `roomId` 可避免暴露多余状态，服务端仍负责校验房间是否可加入。

### 5. 分享加入优先级高于无房间创建，但低于已有未结束房间

如果被邀请玩家已经有未结束房间，服务端不应让他加入第二张未结束牌桌。客户端在大厅中显示“已有牌桌，正在进入原牌桌”或明确错误，而不是静默覆盖。

原因：当前系统已经约束一个玩家只能有一个未结束房间。邀请加入必须尊重这个约束，否则会破坏座位和重连模型。

### 6. 创建房间后不自动开局

`createLobbyRoom` 创建成功后进入等待房间；只有房主点击准备并满足开局条件后，才调用服务端开局。已有自测自动开局路径可保留为内部兼容方法，但不再由大厅创建按钮触发。

原因：邀请好友前必须给房主一个停留状态，否则好友还没来就已经开始 AI 桌。

## Risks / Trade-offs

- 分享进入时小游戏可能已在后台运行 → 同时处理 `getLaunchOptionsSync()` 和 `wx.onShow()`，避免只在冷启动读取参数。
- 邀请房间已满或已开局 → `joinRoom` 返回明确错误，客户端显示可返回大厅的失败状态。
- 房主分享后自己再次点击准备/开局过快 → 服务端必须校验开局条件，客户端按钮状态只是辅助。
- 多人同时通过同一分享加入 → 服务端按最小空座分配，满座后后续请求返回 `ROOM_FULL`。
- 玩家已有其他未结束房间 → 服务端拒绝加入或返回已有房间，客户端优先重连已有房间。
- 只要求房主 ready 可能让好友未点准备也被带入牌局 → 第一版追求最小闭环；后续可改为“所有真人准备后开局”。

## Migration Plan

1. 扩展服务端房间模型，给 `players` 增加 `ready`，并提供等待房间公开快照。
2. 调整创建房间后的客户端流程：创建成功后进入等待房间，不自动 `startRound`。
3. 实现等待房间 UI，包括玩家列表、准备按钮、微信邀请按钮和开局状态。
4. 接入微信分享 query，支持冷启动和回前台读取 `roomId` 并自动加入。
5. 增加准备和开局 action，服务端校验至少 2 名真人且房主 ready。
6. 更新检查脚本覆盖创建等待、邀请参数、加入、准备、开局和错误路径。

## Open Questions

- 后续是否要升级为“所有真人都准备后才开局”？
- 房主是否需要单独的“开始”按钮，还是“准备”按钮满足条件后直接开局？
- 等待房间是否需要显示复制房间号作为分享失败时的 fallback？
