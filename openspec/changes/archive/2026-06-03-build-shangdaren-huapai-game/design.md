## Context

The codebase is a WeChat minigame starter shooter built around one canvas, a frame loop, sprite classes, collision checks, score display, and restart UI. The requested game is a Shang Da Ren flower-card table game with Mahjong-like play, so the implementation needs a new turn-based model instead of incremental changes to the shooter entities.

Shang Da Ren rules have regional variants. The first implementation will use a configurable rules module with a default local-play variant: four seats, one human player, three local AI players, a 24-symbol deck with multiple copies, draw/discard turns, exposed meld actions, self-draw or discard win opportunities, and round summary scoring. Variant-specific details such as special flowers, exact hu/fu thresholds, and local scoring bonuses should be isolated in data tables and evaluators.

## Goals / Non-Goals

**Goals:**

- Deliver a playable single-device Shang Da Ren flower-card round inside the WeChat minigame canvas.
- Replace shooter state with explicit card-game state: deck, hands, discards, melds, current seat, phase, pending action, result, and round history.
- Provide deterministic rule evaluation for legal discards, draw flow, chi/peng/gang-style melds, win checks, and draw-game end.
- Render a responsive card table with clear player hand interaction and visible opponent/discard information.
- Add simple AI that keeps turns moving without remote services.
- Keep assets and audio local, with graceful canvas fallback when a specific image mapping is missing.

**Non-Goals:**

- Online multiplayer, matchmaking, replay sharing, or persistent accounts.
- Complete coverage of every regional Shang Da Ren scoring variant in the first pass.
- Real-money, betting, or wallet behavior.
- Advanced AI search, machine learning, or difficulty personalization.

## Decisions

1. Use a turn-based game engine under `js/game/` instead of adapting the animation/collision loop.

   The engine will expose methods such as `startRound()`, `selectCard()`, `discardSelected()`, `applyAction(action)`, and `advanceTurn()`. `Main` will keep the requestAnimationFrame loop for canvas redraws, but game progression will happen through input and scheduled AI decisions rather than per-frame physics.

   Alternative considered: mutate existing `Player`, `Enemy`, and `Bullet` classes into card concepts. That would keep file count low, but their APIs encode movement, collision, and object pooling assumptions that do not match a card-table game.

2. Model rules as pure functions plus rule configuration.

   Card definitions, meld patterns, priority rules, and win scoring will live in data modules and pure evaluators. This makes it easier to adjust the default variant after playtesting and to unit-check hands without booting the WeChat runtime.

   Alternative considered: encode rule checks directly inside rendering or input handlers. That would be faster to prototype, but would make later local-rule fixes risky.

3. Render the table with canvas primitives first, asset images second.

   The renderer will draw card rectangles, characters, suit/color states, selected-card lift, action buttons, and result overlays even if no card-face atlas is available. Existing manually replaced images can be mapped for background/table/card art as optional enhancements.

   Alternative considered: require a complete atlas before gameplay. That blocks rule implementation on asset naming and makes debugging harder.

4. Keep AI deterministic and transparent for the first release.

   AI will prioritize immediate win, then useful meld responses, then discard the lowest-value isolated card based on simple hand grouping. This is enough to make the game playable and testable while keeping behavior predictable.

   Alternative considered: random-only AI. Random play is easy but often creates broken-feeling rounds and fails to exercise meld/win states reliably.

5. Use one central input router for touch hit-testing.

   Touch handling will map screen coordinates to card slots and action buttons generated by the current layout. This avoids scattering `wx.onTouchStart` logic across renderers and keeps responsive layout consistent.

   Alternative considered: let each UI component register its own WeChat touch listener. That increases lifecycle cleanup risks and duplicate event handling.

## Risks / Trade-offs

- Regional rules may differ from the default implementation → Keep rule constants and winning/scoring evaluators isolated, and document the chosen default in the spec.
- WeChat canvas text rendering may vary across devices → Use large card text, high contrast, measured layout bounds, and fallback fonts.
- AI action timing may feel abrupt → Add a small configurable delay before AI discards or responds.
- Asset filenames are generated UUID-style paths → Build an explicit asset manifest so future replacements only update mapping in one place.
- Complex hand evaluation can become slow if brute-forced → Start with small pure evaluators and cache repeated hand counts during a single action check.

## Migration Plan

1. Introduce card/rule/AI/render/input modules without deleting the current template files.
2. Switch `js/main.js` to initialize the new DataBus state, table renderer, input controller, and game engine.
3. Remove shooter imports and stop creating player, enemy, bullet, background, and collision systems.
4. Update or replace `GameInfo` and `Music` to serve card-table prompts, results, and audio cues.
5. Validate in the WeChat developer tool or a compatible minigame runtime, then remove unused shooter modules if they are no longer referenced.

Rollback is straightforward before deleting unused modules: restore the previous `js/main.js` imports and DataBus shape. After cleanup, rollback should use version control.
