## Context

当前在线入口由启动菜单直接进入 `OnlineController.startSoloOnline`，流程是微信登录、尝试恢复本地缓存房间、失败后创建房间并立即开局。这个流程适合早期单人在线自测，但不适合正式的在线入口：玩家登录后没有大厅承接，也无法主动选择创建房间和局数。

服务端已经有 `rooms`、`roomStates`、`matchQueue` 集合和 `createRoom`、`joinRoom`、`startRound`、`pull` 等动作。现有 `pull` 可以恢复指定房间，但“玩家当前是否有未结束房间”仍依赖客户端本地缓存，不够权威。新流程需要让服务端按 `OPENID` 查询未结束牌桌，客户端只根据服务端结果决定是否自动进入房间。

## Goals / Non-Goals

**Goals:**

- 微信登录成功后始终先显示在线大厅。
- 大厅展示当前玩家的昵称、头像等资料。
- 大厅查询服务端未结束房间；有房间时在大厅内显示进入房间 loading，并自动重连。
- 无未结束房间时，大厅展示创建房间入口，创建动作由用户主动触发。
- 创建房间支持 `2`、`4`、`6` 局选项，并把 `maxRounds` 保存到服务端房间配置。
- 保持现有在线牌桌渲染、`pull`、`roomStates.watch`、心跳和动画回执机制可复用。

**Non-Goals:**

- 不实现“洗两道”。
- 不实现“可算重场”。
- 不实现进圈赔付方式配置。
- 不在本次完成复杂的多局总结算明细 UI；但本次 MUST 在达到 `maxRounds` 后停止继续开新局，并展示最终牌桌结束状态。
- 不恢复单机练习或客户端本地权威牌局流程。

## Decisions

### 1. 登录后先进入大厅，再查询未结束房间

客户端在微信登录成功并拿到玩家资料后，立即切换到大厅视图。大厅进入 `checking-room` 状态后调用服务端新动作查询当前 `OPENID` 是否处于未结束房间。

原因：大厅成为稳定的登录后落点，即使后续重连耗时、失败或没有房间，用户都能看到明确状态，而不是在启动菜单和牌桌之间直接跳转。

备选方案是登录后先查询房间，有房间直接进入牌桌，无房间再显示大厅。该方案跳转更短，但不符合“有房间时也显示大厅，并在大厅显示进入房间 loading”的体验要求。

### 2. 新增服务端 `activeRoom` 查询动作

`game` 云函数新增类似 `activeRoom` 的动作，由服务端在 `rooms` 集合中查找包含当前 `OPENID` 且状态未关闭/未最终结束的房间。返回结构包含：

- `ok`
- `hasRoom`
- `roomId`
- `seat`
- `status`
- `version`
- `settings`

服务端结果是唯一依据；客户端本地 `huapai-online-room` 缓存只能作为辅助，不再决定登录后是否创建房间。

原因：本地缓存可能过期、被清理或指向已关闭房间。服务端查询可以保证跨设备、断线重进和缓存失效时的行为一致。

### 3. 大厅状态显式建模

大厅至少包含以下状态：

- `checking-room`：正在查询未结束房间。
- `reconnecting`：已发现未结束房间，正在 `pull`、订阅并进入牌桌。
- `idle`：没有未结束房间，可以创建房间。
- `creating`：用户已选择局数并正在创建房间。
- `error`：查询、重连或创建失败，允许重试。

原因：这些状态对应真实异步边界，显式建模能避免重复点击、重复创建和重连失败后无入口的问题。

### 4. 创建房间仅接受白名单局数

客户端提供 `2`、`4`、`6` 三个局数选项；服务端也必须校验 `maxRounds` 只能是这些值之一。缺省值使用 `2`，以方便测试。

原因：客户端 UI 不能作为安全边界，服务端校验可以避免非法配置写入房间。先使用少局数选项，符合当前测试诉求，也避免过早暴露完整规则配置。

### 5. 房间配置保存为 `settings`

创建房间时在 `rooms` 文档保存：

```js
settings: {
  maxRounds: 2
}
```

未来的“洗两道”“可算重场”“进圈赔付方式”可以扩展到同一个 `settings` 对象，但本次不创建 UI 或裁决逻辑。

原因：把牌桌规则配置集中在 `settings`，后续扩展不需要重新迁移顶层字段。旧房间没有 `settings` 时按 `{ maxRounds: 2 }` 兼容。

### 6. 达到最大局数后结束牌桌

服务端在每局结果产生后检查当前 `engine.state.round` 是否达到 `room.settings.maxRounds`。若已达到，房间状态切换为 `tableResult`；客户端仍展示当前局结果和累计分，但不再提供“再来一局”入口。后续登录时 `activeRoom` 不再把 `tableResult` 房间视为未结束房间。

原因：`maxRounds` 是创建房间时玩家可见的核心配置，必须影响牌桌生命周期，否则玩家选择 2 局后仍能继续玩会造成规则预期落空。

### 7. 创建后沿用现有自测开局路径

用户主动创建房间后，可以沿用当前“创建好友房后由房主开局，空座 AI 补位”的自测路径进入牌桌。本次重点是创建动作由用户触发，并携带局数配置。

原因：完整等待房间、邀请加入和房主开局 UI 可以后续单独完善；本次变更先替换登录后自动创建的体验，同时保持现有在线牌局可玩。

## Risks / Trade-offs

- 服务端按 `players.openid` 查询数组对象可能受云数据库查询能力限制 → 如果嵌套数组查询不稳定，可以增加 `playerOpenids` 顶层索引字段，创建/加入房间时同步维护。
- 旧房间缺少 `settings` 字段 → 服务端读取时使用默认配置兼容，避免影响已存在测试房间。
- 自动重连失败后用户可能卡在 loading → 大厅需要进入 `error` 状态，展示重试入口；重试时重新调用 `activeRoom` 或再次 `pull`。
- 用户快速重复点击创建房间可能创建多张桌 → 大厅 `creating` 状态禁用按钮，服务端创建前再次检查当前玩家是否已有未结束房间。
- 本次只做最小牌桌结束呈现，不做完整总结算明细 → 结果页需要明确不可继续开局，后续再补总榜、明细和退出大厅体验。

## Migration Plan

1. 新增服务端 `activeRoom` 动作并保持现有 `pull`、`createRoom`、`startRound` 行为兼容。
2. 扩展 `createRoom` 接收并保存 `settings.maxRounds`，旧调用缺省为 `2`。
3. 新增或改造客户端大厅 UI，使在线入口登录后进入大厅，而不是直接自动建房。
4. 在大厅中接入 `activeRoom` 查询、重连 loading、创建房间局数选择和创建状态。
5. 保留本地房间缓存用于牌桌内快速恢复，但登录后是否进入房间以服务端 `activeRoom` 为准。

回滚时可以恢复旧 `startSoloOnline` 入口；服务端新增字段和动作向后兼容，不需要删除已有房间数据。

## Open Questions

- 创建房间后是否继续自动 `startRound` 并用 AI 补空座，还是进入等待房间等待玩家手动开局？本设计按“沿用现有自测开局路径”处理，后续可单独提出等待房间体验。
- `maxRounds` 达到后完整牌桌总结算的 UI 和服务端状态应在后续 change 中细化。
