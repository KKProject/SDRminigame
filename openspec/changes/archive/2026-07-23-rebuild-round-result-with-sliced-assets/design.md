## Context

当前结果页将 `images/round_result_bg.jpg` 作为整屏背景，再通过 Canvas 绘制标题、状态、白板区域、玩家条目和按钮。用户已提供五类透明 PNG 切图：结果标题、胜利/失败状态、白板面板、继续游戏及再来一局按钮。原始切图合计约 1.30 MB，其中白板约 1.01 MB；当前微信小游戏上传主包约 3.10 MB，直接加入全部原图会让主包失去发布余量。

结果页同时需要适配不同横屏安全区和最多四个高条目。白板切图包含不可变形的四角与边框，不能简单按目标矩形整体拉伸；玩家条目仍需在白板内部纵向滚动，标题、房号局数和主按钮保持固定。

## Goals / Non-Goals

**Goals:**

- 在保留透明通道和文字清晰度的前提下处理并引入结果页切图。
- 复用现有 `images/background.jpg`，用透明切图组合出更接近设计稿的结果页。
- 将白板作为九宫格资源绘制，使边框和四角在不同安全区宽度下不变形。
- 保留既有四家牌况、纵向 mini 牌、胡牌玩家最终胡数、本局分数和滚动交互。
- 通过删除被替代资源和定向压缩大图，将实际微信上传主包控制在 4 MiB 以下，并以不高于约 3.7 MiB 为目标保留余量。

**Non-Goals:**

- 不实现分享战绩、保存回放、返回大厅或总战绩页面。
- 不修改服务端结算结构、实时同步协议、胡数计算或下一局确认流程。
- 不把“再来一局”按钮解释为“查看战绩”，也不在本 change 中新增最终房间重开语义。
- 不重做牌面 atlas、头像系统或游戏桌面其他页面。

## Decisions

### 1. 按资源特性分别优化，而不是统一缩放

标题、胜负状态和按钮切图体积较小且包含文字，保留原始 @2x 尺寸；仅对白板大图进行尺寸和调色板优化。处理后的每张 PNG 必须仍含有效 alpha 通道，白板应优先选择兼顾清晰度与体积的候选，并通过实际渲染截图确认渐变和金色边框没有明显色带。

备选方案是全部缩小 50%，其体积更小，但在 Canvas 像素比为 2 的设备上会降低文字与装饰清晰度，因此不采用。

### 2. 复用牌桌背景并移除整屏结果页 JPG

结果页底层继续绘制已经随主包发布的 `images/background.jpg`，其上叠加透明切图。新页面稳定后删除被完全替代的 `images/round_result_bg.jpg`，回收约 0.29 MB，避免两张相似全屏背景同时占用主包。

### 3. 白板采用运行时九宫格绘制

为 Canvas 增加通用九宫格绘制辅助逻辑。根据白板源图测得并固定四边保护区，将源图拆成九块：

```text
┌──────┬────────────────┬──────┐
│ 左上 │      上边      │ 右上 │
├──────┼────────────────┼──────┤
│ 左边 │   可伸缩中心   │ 右边 │
├──────┼────────────────┼──────┤
│ 左下 │      下边      │ 右下 │
└──────┴────────────────┴──────┘
```

四角保持源比例，边缘只沿单一方向拉伸，中心填充剩余空间。绘制目标使用安全内容区域内的结果面板矩形，不依赖某一固定屏幕宽高。

备选方案是直接缩放整张白板，代码更少，但会使角花、流苏和边框粗细随屏幕比例变形，因此不采用。

### 4. 切图只负责装饰和固定文案，动态数据继续由 Canvas 绘制

`对局结果.png`、`胜利.png`、`失败.png`、`继续.png` 作为独立语义资源加载。玩家昵称、牌况、标签、胡数、本局分数、房号和局数仍由现有数据驱动绘制，避免为动态内容制作图片。

胜负状态按本机玩家视角显示：本机是胡牌赢家时使用“胜利”，胡牌但本机不是赢家时使用“失败”。进圈、流局和荒庄没有对应切图时继续使用 Canvas 状态文案，不强行套用胜负资源。

玩家最终剩余手牌按权威牌数据中的 `phraseId` 归组：同一句话中的不同牌面共用一个纵向叠放列，只有不同句子才横向换列。吃、碰、招、踏等公开牌组仍按每个 meld 独立成列，避免把动作牌组与剩余手牌混合。

### 5. 保持既有操作语义并提供资源回退

未达到最大局数时，唯一主按钮沿用“继续下一局”行为，并优先绘制 `继续.png`。最终局仍显示“查看战绩”，由于当前切图中没有对应资源，继续使用 Canvas 按钮回退；`再来一局按钮.png` 暂不接入交互。

任一结果页切图加载失败时，只回退对应元素，不阻塞结果数据、滚动或按钮点击。布局和命中区域以逻辑矩形为准，不以图片非透明像素边界为准。

### 6. 以实际上传结果作为包体积验收依据

文件系统大小只用于预估。实现完成后使用项目指定的 Node 20 上传流程或等价的 CI 预览获取 `subPackageInfo.__FULL__`，确认主包低于 4 MiB，并以约 3.7 MiB 或更小为目标。若超出目标，先继续优化白板调色板/尺寸或清理被替代资源，不降低标题和按钮文字清晰度。

## Risks / Trade-offs

- [白板调色板压缩产生色带或金边锯齿] → 生成多个压缩候选，在至少一台高像素比真机或等效截图中比较后再选定。
- [九宫格保护区选取不准导致接缝] → 从透明边界和装饰内缘测量切线，并在窄屏、宽屏及不同像素比下截图检查。
- [切图透明留白影响视觉尺寸或命中区域] → 绘制尺寸按切图内容比例校准，交互命中始终使用独立布局矩形。
- [新增资源使主包逼近 4 MiB] → 删除旧整屏 JPG、只优化大图，并以实际上传包体而非源目录大小验收。
- [胜负切图无法表达非胡牌结果] → 进圈、流局和荒庄保留 Canvas 状态文案，后续有专用切图时再扩展。
- [最终局按钮视觉暂时不完全统一] → 保留正确的“查看战绩”语义和 Canvas 回退，优先保证流程正确。

## Migration Plan

1. 从外部切图目录生成并检查透明 PNG 候选，只将最终选定资源复制到项目资源目录。
2. 更新资源清单与加载回退，并实现九宫格绘制辅助能力。
3. 将结果页改为复用牌桌背景并组合切图，保留现有动态内容与滚动逻辑。
4. 完成截图、交互和回归验证后删除被替代的 `round_result_bg.jpg`。
5. 运行项目测试并检查实际微信上传包体；若失败，可恢复旧资源映射和旧结果页绘制路径回滚。

## Open Questions

- 后续若提供“查看战绩”专用透明 PNG，可直接替换 Canvas 回退，不改变本 change 的按钮行为。
- `再来一局按钮.png` 是否用于最终战绩页或房间重开流程，留待对应产品范围单独定义。
