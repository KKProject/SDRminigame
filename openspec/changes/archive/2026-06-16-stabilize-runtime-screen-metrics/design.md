## Context

项目通过 `game.json` 请求横屏运行。当前 `js/render.js` 在模块加载时调用一次 `wx.getWindowInfo()` 或 `wx.getSystemInfoSync()`，随后将逻辑宽高、安全区和像素比导出为不可变常量，并立即设置 Canvas backing store。`TableRenderer`、`TableLayout` 和启动菜单在构造时读取这些常量，此后没有窗口尺寸更新入口。

部分真机启动时，微信运行时会在横屏尚未稳定前返回临时窗口信息，例如宽高仍接近竖屏、宽高过小或安全区属于另一方向。Canvas 和背景后续可能由运行时正常铺满，但牌桌布局继续使用首次读取的错误尺寸，因此 UI 元素挤在一起。

## Goals / Non-Goals

**Goals:**

- 只使用经过校验且已经稳定的横屏窗口指标创建正式菜单和牌桌布局。
- 在窗口宽高、像素比或安全区发生有效变化时，原子更新 Canvas、context、菜单、牌桌布局、命中区域和动画目标。
- 异常或过渡指标不得覆盖最后一份稳定指标；首次启动尚无稳定指标时，仅显示全屏背景或轻量等待状态。
- 对重复相同指标通知保持幂等，避免每帧反复重建布局。
- 保持背景始终覆盖完整 Canvas，内容元素继续遵守安全区。

**Non-Goals:**

- 不支持把正常牌局切换为纵屏布局。
- 不修改牌局状态、手牌分列规则、在线协议或服务端逻辑。
- 不修改背景图和牌面资源。
- 不通过写死具体手机型号或屏幕尺寸进行适配。

## Decisions

### 1. 引入可变的运行时渲染指标管理器

`render.js` 不再只导出启动时快照，而是维护当前稳定 `RenderMetrics`，并提供：

- 读取候选窗口指标；
- 校验与生成候选签名；
- 提交稳定指标并重新配置 Canvas/context；
- 查询当前稳定指标；
- 订阅指标变化。

布局、菜单和主循环通过查询或订阅获取最新指标，不再长期持有启动期宽高常量。

选择集中管理，是因为 Canvas backing store、逻辑坐标、安全区和布局必须使用同一份指标原子更新。让各模块分别调用微信 API 容易产生一帧内尺寸不一致。

### 2. 横屏候选指标必须通过有效性与稳定性检查

候选指标至少需要满足：

- 宽高、像素比为有限正数；
- 游戏请求横屏时逻辑宽度大于逻辑高度；
- 安全区经过现有边界校验后仍有有效内容区域；
- 候选与当前稳定指标相比确实发生变化。

启动阶段要求同一有效候选连续出现两次，或由 `wx.onWindowResize` 提供后再次读取确认，才提交为稳定指标。异常、竖屏过渡或明显不完整的候选只记录但不提交，并在后续动画帧重试。

备选方案是直接交换错误的宽高。该做法无法同步修正安全区方向，可能把错误数据伪装成横屏，因此不采用。

### 3. 首次稳定前不创建正式交互布局

如果首次读取未得到稳定横屏指标，主循环仍可以按当前 Canvas 绘制全屏背景或等待画面，但不得创建正式菜单按钮、牌桌元素或命中区域。稳定指标提交后，再创建或更新菜单与牌桌布局。

这样可以避免玩家在临时错误区域点击，也避免错误布局状态被手牌稳定分列逻辑长期保存。

### 4. 指标提交采用原子重配置顺序

提交新的稳定指标时按以下顺序处理：

1. 更新 Canvas backing-store 宽高；
2. 使用 `setTransform` 重新建立逻辑像素缩放，避免重复累乘；
3. 更新稳定指标快照；
4. 通知菜单、渲染器和布局使用新逻辑宽高与安全区；
5. 重建命中区域和下一帧布局。

背景继续使用完整逻辑宽高绘制，安全内容区域只约束其他 UI 元素。

### 5. 尺寸变化时取消坐标相关临时动画

活动动画的起点、终点和临时视觉对象都绑定旧布局坐标。稳定指标变化时，动画控制器必须取消活动 Tween、清理旧临时视觉和旧完成回调，再由最新牌局状态或权威事件在新布局中恢复必要的等待牌和静态显示。

不尝试在动画中途按比例换算坐标，因为不同安全区和布局规则并非简单等比缩放，换算后仍可能落错位置。

### 6. 窗口变化监听与帧轮询共同兜底

主程序注册一次 `wx.onWindowResize`，收到通知后立即触发候选指标读取；启动未稳定期间和检测到异常候选后的短时间内，主循环按有限次数或退避策略重新读取。指标稳定后停止持续轮询，避免每帧调用微信 API。

## Risks / Trade-offs

- [尺寸稳定确认会让极少数设备启动时短暂只显示背景] → 使用连续两次读取确认，通常仅延迟一到数帧，并优先保证布局正确。
- [窗口变化时取消动画会中断当前视觉过程] → 从最新权威状态恢复等待牌或静态牌，避免继续播放到错误位置；牌局状态与服务端推进不受影响。
- [重复设置 Canvas 宽高会清空绘制状态] → 仅在稳定指标签名变化时重配置，并在同一次提交中立即恢复 context transform。
- [微信不同基础库提供的窗口 API 不一致] → 继续保留 `getWindowInfo`、`getSystemInfoSync` 和无监听能力环境的兼容路径。
- [菜单原生授权按钮仍使用旧坐标] → 指标变化通知菜单销毁并按新按钮区域重建原生授权按钮。

## Migration Plan

1. 将 `render.js` 改造成可测试的运行时指标管理器，同时保留现有指标计算函数。
2. 修改 `Main`、`StartMenu`、`TableRenderer` 和 `TableLayout`，接收最新稳定指标并支持重布局。
3. 增加尺寸变化时动画清理和权威状态恢复。
4. 扩展自动检查，模拟异常首帧、稳定横屏、重复通知、安全区变化和高像素比。
5. 使用微信开发者工具与至少一台曾复现问题的真机验证冷启动、切后台恢复和横屏方向变化。

## Open Questions

- 无。具体重试间隔和最大启动等待时间可在实现时根据真机日志微调，但不得在异常指标上创建正式交互布局。
