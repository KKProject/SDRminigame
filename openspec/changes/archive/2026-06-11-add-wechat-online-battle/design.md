## Context

现状：花牌（上大人）是微信「小游戏」（`project.config.json` 中 `compileType: "game"`，appid `wx487628e952ff200d`），目前完全本地运行：

- `js/game/engine.js`（约 760 行）是权威状态机，推进 `PHASES`（接庄、出牌、响应、AI 思考、结算）。
- `js/game/rules.js`、`js/game/evaluator.js` 是纯逻辑（建牌、发牌、合法性、胡牌判定、计分）。
- `js/databus.js` 是单例状态容器；`js/game/renderer.js` 渲染、`js/game/input.js` 把触摸事件直接调用引擎方法改状态。
- `js/game/ai.js` 是本地对手决策。

约束：

- 运行环境是微信小游戏（非小程序），无 `wxml`，UI 全部 Canvas 自绘。
- 服务端限定使用微信小程序云开发（云函数 + 云数据库 + 实时数据推送）。
- 现有客户端逻辑用 ES Module；云函数运行在 Node.js（CommonJS）。
- 牌局是回合制，对延迟不敏感（秒级可接受），但对「权威性/防作弊」和「手牌保密」敏感。

## Goals / Non-Goals

**Goals:**

- 玩家进入即完成微信登录，建立服务端身份（OPENID），并展示昵称、头像。
- 真人之间可匹配进入同一牌局，服务端为唯一权威，集中托管牌局状态机、规则与计分。
- 客户端退化为薄客户端：只渲染服务端下发的权威状态、把玩家操作作为「意图」上报。
- 支持断线重连：重连后从服务端恢复当前牌局视图。
- 手牌等私密信息不泄露给其他玩家。
- 保留单机练习模式作为离线回退。

**Non-Goals:**

- 不做排行榜、社交关系链、对局回放、付费道具等运营功能（后续可单独提案）。
- 不追求实时动作类的低延迟同步（回合制秒级延迟可接受）。
- 不在本次变更改动花牌玩法规则本身（仅迁移执行位置）。
- 不实现跨服/分区、弹性扩缩容等大型后端架构。

## Decisions

### 决策 1：服务端形态 = 云函数（权威裁决）+ 云数据库实时推送（状态下发）

- 操作意图通过云函数提交：云函数用 `wx-server-sdk` 的 `cloud.getWXContext().OPENID` 鉴定身份，对照权威状态校验合法性后推进牌局并写回数据库。
- 状态下发用云数据库「实时数据推送」（`db.collection().watch()`）：客户端监听本局的公共状态文档，服务端写入即推送。
- 备选：云托管 + WebSocket（更低延迟、更灵活）。**否决理由**：回合制不需要、引入额外基础设施与成本；优先用云开发原生能力满足「使用微信云服务」的要求。若后续延迟/并发不达标再升级。

### 决策 2：状态切分为「公共状态」与「私密状态」，避免手牌泄露

- `watch` 会把整份文档推给所有监听者，无法按席位隐藏字段。因此把牌局状态拆为：
  - 公共状态文档（可被本局所有玩家 `watch`）：阶段、当前行动席、各席公开信息（昵称/头像/在线/已亮牌/分数）、最近弃牌、将牌、待响应动作摘要等。
  - 私密手牌：仅通过云函数按 OPENID 返回给本人（拉取式），或写入「每席一份、仅本人可读」的数据库安全规则文档。
- **否决「整局明文一份文档」**：会让任何客户端读到别人手牌，破坏防作弊目标。

### 决策 3：权威逻辑（rules/evaluator/engine-core）移植到云函数为唯一真相

- 把 `rules.js`、`evaluator.js` 以及 `engine.js` 中纯粹的状态推进逻辑抽取为「框架无关的核心」，以 CommonJS 形式部署到云函数；客户端不再保留可改变权威状态的逻辑。
- 客户端 `engine.js` 重构为「控制器」：负责发起登录/匹配、上报操作意图、订阅状态、把服务端快照写入 `databus`（镜像）。`databus` 不再被本地业务逻辑直接 mutate。
- 备选：客户端做乐观预测 + 服务端校正。**否决理由**：增加复杂度且回合制收益低，先做「纯权威 + 直接渲染」。

### 决策 4：身份与资料获取

- 身份：`wx.login` 取 code →（云函数侧由 `wx-server-sdk` 直接获取 OPENID，无需自管 session）。用户记录存云数据库 `users` 集合。
- 资料（昵称/头像）：使用微信当前可用的头像昵称获取能力（小游戏 `UserInfoButton` / 头像昵称填写能力），失败或拒绝授权时回退默认头像与「玩家+随机后缀」昵称，并允许后续在设置里补填。
- 备选：`wx.getUserProfile`。**否决理由**：该接口已被微信收回，返回匿名数据，不可靠（见风险）。

### 决策 5：匹配与房间

- 提供两种入口：快速匹配（匹配队列集合 + 匹配云函数撮合到一张牌桌）与好友房间（房主创建房间码、其他人凭码加入）。
- 满座由服务端开局；不足座位可由服务端托管 AI 填充（复用移植后的 AI）。
- 座位与房间生命周期由服务端维护，含「准备/进行中/结算/关闭」。

### 决策 6：断线与托管

- 客户端重连后调用云函数拉取当前牌局快照并重新 `watch`。
- 玩家超时未操作或掉线超阈值，服务端用 AI 托管其席位推进，避免卡局。

## Risks / Trade-offs

- [微信资料接口收紧：`getUserProfile` 返回匿名数据] → 用头像昵称填写/`UserInfoButton` 能力，授权失败回退默认资料，不阻塞进入游戏。
- [云数据库 `watch` 的连接数/写入频率/延迟限制] → 回合制写入频率低；只 `watch` 公共状态精简文档；超限再评估云托管 WebSocket。
- [手牌等私密信息泄露] → 严格切分公共/私密状态 + 数据库安全规则按 OPENID 限制读取；私密数据只经云函数下发。
- [ESM→CJS 逻辑移植引入回归] → 抽取纯函数核心并配套服务端单测；客户端单机模式复用同一份核心校验一致性。
- [并发写同一牌局产生竞态] → 云函数内对房间状态做版本号/乐观锁校验，拒绝过期版本操作。
- [云开发配额与成本] → 评估月活与调用量，开局/操作合并写、精简文档体积。
- [离线/弱网体验] → 明确加载与重连提示；保留单机模式兜底。

## Migration Plan

1. 开通云开发环境，初始化 `cloud.init`，建立 `users`、`rooms`、`matchQueue` 集合及安全规则。
2. 移植纯逻辑核心（rules/evaluator/engine-core）到云函数并补服务端单测，确保与现有本地结果一致。
3. 落地登录与资料能力（客户端 + `login` 云函数 + `users` 写入）。
4. 落地匹配/房间与状态同步协议（匹配、开局、操作上报、`watch` 公共状态、私密手牌下发）。
5. 客户端重构 `engine.js`/`databus.js`/`input.js` 为薄客户端，新增「在线对战 / 单机练习」入口。
6. 灰度：默认保留单机入口可用；在线模式先内部验证再放开。
- 回滚策略：在线入口可一键关闭，回退到纯单机模式（移植不删除客户端单机核心）。
