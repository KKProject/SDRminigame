## Context

当前启动页的 `StartMenu.ensureStartAuthCheck()` 会在菜单显示时检查微信资料授权；若已授权，会立即触发 `startLogin` 调用后端登录。未授权时，启动页显示登录提示并创建透明 `UserInfoButton`。分享进入时，`Main.handleInviteRoomId()` 会直接用 `profileWithFallback()` 启动在线流程，这可能绕过头像昵称门禁。另外，后端现有登录合并逻辑会在 code-only 登录时把已有头像昵称覆盖为空，不利于把数据库里的用户资料作为后续登录来源。

产品现在希望把“微信头像昵称”作为玩家身份初始化的必要条件：玩家本地未获取过头像昵称时，客户端先用 `wx.login` 做 code-only 后端登录恢复数据库资料；后端已有头像昵称则直接视为已初始化；本地和后端都没有资料时，任何进入创建房间或分享房间的入口都必须先提示并完成微信资料登录。已获取过头像昵称时，不再重复请求微信资料，只在用户点击开始或分享意图需要执行时调用后端登录。

## Goals / Non-Goals

**Goals:**

- 将启动页身份状态收敛为“未获取资料 / 获取中 / 已有资料 / 后端登录中 / 登录失败”。
- 首页未有头像昵称时先静默登录后端恢复资料；恢复不到时显示微信登录提示，并让开始按钮区域承接微信资料授权。
- 点击“开始”时执行统一门禁：先确保头像昵称，再后端登录，再进入创建房间页。
- 分享进入时保存 `roomId` 意图；未获取资料时留在启动页提示登录，登录成功后继续加入分享房间。
- 后端 code-only 登录不得清空已保存头像昵称，且应把已保存资料返回给客户端。
- 修复 `getAuthorizedProfile()` 中资料缺失 toast 的异常代码。
- 用回归测试锁住：不重复请求微信资料、分享登录后续接、分享失败只 toast。

**Non-Goals:**

- 不改变后端 `login`、`activeRoom`、`joinRoom` 接口协议字段，仅调整 `login` 对空资料的合并语义。
- 不改变等待页、游戏页和房间规则创建字段。
- 不在本次实现新的手机号、账号密码或后台账号登录。

## Decisions

### 1. 用“待执行意图”驱动登录后的下一步

推荐在 `Main` 中保存当前入口意图，例如创建房间或加入分享房间。`StartMenu` 只负责收集头像昵称并通知 `Main`，不负责决定登录后跳转到哪里。

```text
用户点击开始 / 分享进入
  -> Main 设置 pending intent
  -> Main 用 code-only login 尝试恢复后端头像昵称
  -> StartMenu 在恢复失败时确保头像昵称
  -> Main 调后端 login
  -> Main 根据 intent 进入创建页 / 等待页 / 游戏页 / 启动页 toast
```

这样可以避免“授权成功只把按钮变 ready，但忘了继续执行分享入房”的状态分叉。

### 2. 首页可以自动提示，但不能自动绕过微信授权按钮

微信小游戏获取头像昵称需要用户点击 `createUserInfoButton` 承接。进入首页时未有本地头像昵称，客户端应先通过后端 code-only 登录恢复已有资料；恢复不到时再显示登录提示态，并让可点击区域覆盖微信授权按钮；不应使用 fallback 昵称直接进入创建房间或分享房间。

### 3. 后端资料是后续登录的稳定来源

后端 `login` 接口收到空 profile 时，只更新 `lastLoginAt`，不得把已有 `nickName` / `avatarUrl` 覆盖为空。收到部分资料时只更新非空字段，避免一次缺失头像或昵称的请求清掉另一项。客户端 code-only 登录拿到后端资料后写入启动页状态，后续开始/分享流程不再请求微信资料。

### 4. 已有头像昵称时不重复请求微信资料

本地缓存里已有头像或昵称时，启动页可进入“已准备”态。点击开始或分享续接时直接调用后端登录。若后端登录失败，仍停留启动页并允许重试，不清除本地头像昵称。

### 5. 分享意图优先于普通创建意图

分享进入时如果用户未完成资料初始化，启动页提示“请先微信登录后进入房间”。登录成功后优先处理 `pendingInviteRoomId`，而不是进入创建房间页。若房间不存在或已结束，只 toast 并清理分享意图，停留启动页。

### 6. 测试既覆盖行为，也覆盖危险源码模式

`scripts/run-online-checks.mjs` 需要增加行为级用例，验证已缓存资料时点击开始不会创建微信资料按钮，以及本地无资料时先 code-only 恢复后端资料；也增加源码守护，防止重新引入 `profileWithFallback()` 绕过分享登录门禁，或把分享失败消息写回按钮下方 status。`scripts/run-backend-checks.mjs` 需要覆盖 code-only 登录不清空已保存资料。

## Risks / Trade-offs

- [Risk] 微信 `createUserInfoButton` 在部分环境不可用。→ Mitigation: 保持可重试提示；开发环境可用测试替身验证流程，真机验收以微信能力为准。
- [Risk] 本地缓存资料过旧。→ Mitigation: 本次只满足“不重复请求”；后续如需刷新头像昵称，可单独设计“资料更新”入口。
- [Risk] 当前启动页状态和 `Main.mode` 双状态容易漂移。→ Mitigation: 让 `Main` 统一执行 intent，`StartMenu` 只暴露授权/点击事件。
- [Risk] code-only 静默登录增加一次首页网络请求。→ Mitigation: 只在本地没有头像昵称时触发，并复用返回的后端资料完成门禁。

## Migration Plan

1. 更新 OpenSpec delta，明确启动页资料门禁和分享续接行为。
2. 调整 `StartMenu` 的启动页登录状态和开始按钮处理。
3. 调整 `Main` 的分享入口和登录后意图执行。
4. 修复 `js/net/profile.js` 资料缺失分支。
5. 补充并运行在线流程回归。
6. 部署后端并上传微信小游戏供真机验收。

回滚策略：若发布后登录入口异常，可恢复上一个小游戏上传版本；后端协议和数据不变，无需数据回滚。
