## Context

当前在线牌局在 `phase=result` 时仍绘制牌桌，并在中央约 `420×180` 的区域显示简略结果和“再来一局”按钮。公共状态的 `seats` 只暴露 `handCount`，`buildPrivateView` 只向本人下发完整手牌；因此客户端无法渲染四家最终牌况。普通非最终局由房主调用 `startRound` 直接开下一局，其他玩家没有独立的查看完成状态。

本次设计参考已确认的横屏结果页效果：红金标题、米色主面板、四名玩家逐行牌况、本家高亮以及右下角唯一主操作。项目为四人局，页面必须在现有横屏安全区内同时容纳四行牌况，并继续使用现有花牌 atlas、头像和酒楼背景。

## Goals / Non-Goals

**Goals:**

- 在终局动画完成后切换到独立的全屏单局结果页，展示四家最终剩余手牌、公开牌组和本局分数。
- 仅为胡牌玩家展示权威最终胡数，其他玩家显示 `--`；不展示累计得分。
- 进行中继续保护其他玩家手牌，仅在权威结果阶段公开冻结牌况。
- 普通局间由所有真人确认“继续下一局”后自动开局，并支持重连恢复确认状态。
- 最终局只展示“查看战绩”入口，为后续总战绩页面保留稳定接点。

**Non-Goals:**

- 不实现总战绩页面及其数据汇总。
- 不实现分享战绩、保存回放或回放协议。
- 不在结果页提供返回大厅入口。
- 不调整胡牌、进圈、流局、荒庄的规则判定和计分算法。
- 不展示或重新计算房间累计得分。

## Decisions

### 1. 使用结果阶段专用 `roundDetail`，不扩展进行中的公共手牌

服务端在权威状态进入 `phase=result` 后构建结果专用公共字段：

```text
roundDetail
├── round
├── maxRounds
├── hasNextRound
├── resultType
├── players[]
│   ├── seat
│   ├── finalHand[]
│   ├── melds[]
│   ├── roundScore
│   └── huCount
└── continuation
    ├── requiredSeats[]
    ├── confirmedSeats[]
    └── selfConfirmed
```

`finalHand` 从结果时的服务端权威座位手牌复制，`melds` 复用已经公开的凑牌数据，`roundScore` 使用权威 `result.roundScores`。仅当 `result.type=win` 且当前座位为赢家时，`huCount` 取权威 `result.scoring.totalFu`；其他座位为 `null`，客户端显示 `--`。

选择独立 `roundDetail` 而不是给公共 `seats` 永久增加 `hand`，是为了让隐私边界可审计：任何非结果阶段的 snapshot/delta 都不得携带完整对手手牌。下一局开始时该字段必须消失。

### 2. 结果页服从现有终局动画显示闸门

权威镜像可以先进入结果阶段并收到 `roundDetail`，但渲染状态必须等 `hu`、`circle-loss` 或 `draw-round` 事件完成、快进或跳过后一次性提交。这样不会重现结果 UI 抢在终局动画前出现的问题。

客户端将 `roundDetail` 映射为本机座位始终位于固定“本家”行的显示模型，所有 seat 引用、分数和确认状态都随现有座位旋转逻辑转换。

### 3. 结果页采用独立全屏布局

结果页覆盖牌桌操作层但继续使用横屏背景和安全区。布局从上到下分为：

- 红金“对局结果”标题和胡牌、进圈、流局或荒庄副标题；
- 米色四行玩家面板；
- 每行头像昵称、角色标签、最终牌况、胡数、本局分数；
- 底部房号、当前局数/最大局数和右下角唯一主按钮。

本家行使用金黄色底色和“本家”标签；胡牌玩家使用“本局玩家”标签及醒目的“胡”标识。最终手牌按现有句子和牌字顺序使用固定可辨认尺寸的 mini 牌纵向分列堆叠，凑牌上方显示吃、碰、招、踏动作标签。玩家条目使用能够容纳纵向叠牌的最小高度；四个玩家条目的总高度超过主面板时，主面板内的玩家结果列表整体支持纵向拖动浏览，标题、底部信息和唯一主按钮保持固定。结果列表左右边界按整屏背景主面板比例定位后再与设备安全区求交，避免刘海安全区偏移被重复计入而使列表比背景空白区明显偏窄。页面不得通过压缩条目高度牺牲牌面辨识度，也不得绘制累计得分、分享、回放或返回大厅控件。

结果页需要新增可九宫格拉伸或等价绘制的标题、主面板、玩家行、标签和主按钮资源。牌面、头像边框及背景优先复用现有资源；资源未就绪时必须有不影响信息可读性的 Canvas 降级绘制。

### 4. 普通下一局使用独立的全员确认状态

普通 `finished` 房间新增按 `round` 绑定的继续确认记录，和最大局数后的 `rematch` 重开确认分开，避免“下一局”和“重开一轮”语义混合。需要确认的成员只包含仍占用房间座位的真人，AI 不进入等待集合。

任意真人点击“继续下一局”时提交幂等确认；服务端记录后广播最新确认摘要。当全部所需真人均确认且房间仍是同一局的 `finished` 状态时，服务端原子地开始下一局。客户端确认后将按钮显示为不可重复提交的等待状态，但页面继续可查看。

最终局 `hasNextRound=false`，不得创建普通继续确认，也不得调用 `startRound`。结果页只显示“查看战绩”。本次点击该按钮仅显示“战绩功能待开放”反馈并保持当前页，后续 change 再接入总战绩页面。

### 5. 结果恢复以服务端为唯一权威

`roundDetail` 和继续确认记录随房间结果状态持久化，并通过 HTTPS 快照与 WebSocket snapshot/delta 返回。重连客户端不得从本地牌桌推导其他玩家手牌或确认状态；重复确认必须幂等，迟到的上一局确认必须按局号拒绝。

## Risks / Trade-offs

- [四家完整牌况在窄屏上拥挤] → 使用有最小高度的玩家条目、mini atlas、纵向分列和主面板纵向滚动，并以最窄支持设备做截图与手势回归。
- [终局手牌被过早公开] → `roundDetail` 只允许在 `phase=result` 序列化，增加进行中 snapshot/delta 不含对手牌的协议测试。
- [确认请求与下一局启动并发] → 确认记录绑定局号并在房间写锁内幂等合并，最后一次确认与 `startRound` 使用同一原子生命周期更新。
- [玩家断线导致下一局等待] → 保留服务端确认状态并允许重连继续确认；自动确认或超时托管不在本次范围内。
- [最终局暂无可进入的战绩页] → “查看战绩”提供明确待开放反馈且不误启动下一局，后续 change 替换该占位行为。
- [新增美术资源增加包体] → 优先使用可拉伸小图和现有背景、牌面资源，并检查小游戏主包体积。

## Migration Plan

1. 先部署兼容旧客户端的服务端字段和确认接口；旧客户端可忽略新增 `roundDetail`。
2. 发布支持全屏结果页的新客户端，并通过协议版本或字段存在性选择新结果流程。
3. 验证新旧客户端混房时不会因旧客户端无法确认而永久等待；必要时发布窗口内限制同房协议版本。
4. 回滚客户端时服务端继续保留旧房主 `startRound` 兼容路径；确认稳定后再移除兼容分支。

## Open Questions

- 后续“查看战绩”页面是展示当前房间全部局次，还是只展示四家最终总分，需要在独立 change 中确定。
- 是否为断线玩家增加继续确认超时或托管，需要结合真机房间等待体验另行决定。
