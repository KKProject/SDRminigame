## ADDED Requirements

### Requirement: 并发响应窗口裁决
服务端权威状态机 SHALL 为存在响应机会的出现牌创建并发响应窗口。响应窗口 MUST 记录每个可响应席位的合法动作、响应状态和选择结果；服务端 MUST 只接受窗口内对应席位提交的合法响应意图，并 MUST 在当前最佳选择无法被未决候选推翻时立即裁决。裁决后，服务端 MUST 清空响应窗口、使其他未决响应失效，并应用唯一胜出的胡、吃、碰、招或踏动作；若所有席位均过牌或无可用选择，服务端 MUST 将出现牌按无人响应处理。

#### Scenario: 多个真人同时响应
- **WHEN** 同一张出现牌可被多个真人席位响应
- **THEN** 服务端 MUST 在同一个响应窗口内向每个真人开放其本人合法响应
- **AND** 任一真人的响应选择 MUST NOT 依赖更早响应顺序真人先提交过牌

#### Scenario: 当前最佳选择提前裁决
- **WHEN** 服务端收到一个合法响应选择
- **AND** 所有未决候选动作都无法按优先级和响应顺序击败该选择
- **THEN** 服务端 MUST 立即裁决该选择为胜出动作
- **AND** 服务端 MUST 取消同一响应窗口内其他未决动作

#### Scenario: 所有人过牌
- **WHEN** 响应窗口内所有候选席位均选择过牌、被托管过牌或因规则结果失去响应资格
- **THEN** 服务端 MUST 按无人响应处理当前出现牌
- **AND** 服务端 MUST 只生成最终归位事件，不为每个过牌生成公开动作事件

#### Scenario: 过期响应被拒绝
- **WHEN** 响应窗口已经裁决或版本已经更新后，客户端提交旧窗口的响应意图
- **THEN** 服务端 MUST 拒绝该意图且不改变权威状态
- **AND** 服务端 MUST 返回足以让客户端同步最新快照的错误信息

## MODIFIED Requirements

### Requirement: 服务端公开操作事件
服务端权威牌局状态机 SHALL 为每一次对牌桌玩家可见的状态推进生成公开操作事件。每个事件 MUST 包含房间内单调递增的事件序号、事件类型、对应状态版本、行动席位和完成该动画所需的公开信息；事件 MUST NOT 包含任何尚未公开的其他玩家手牌信息。抓牌和出牌事件 MUST 包含公开的 `appearanceResolution` 动画分支；凑牌事件 MUST 包含稳定的 meld id 和最终公开牌组。响应窗口中的私有过牌选择 MUST NOT 生成公开操作事件；只有最终无人响应时才生成归位事件。

#### Scenario: 初始无人响应合并为复合事件
- **WHEN** 服务端在生成抓牌或出牌事件时已经确定无人可以响应该牌
- **THEN** 服务端 MUST 将该牌最终进入弃牌区的状态提交到权威快照
- **AND** 服务端 MUST 生成 `appearanceResolution` 为 `auto-discard` 的单个抓牌或出牌事件
- **AND** 服务端 MUST NOT 为同一次初始无人响应额外生成独立 `unclaimed` 动画事件

#### Scenario: 有响应机会的出现牌事件
- **WHEN** 服务端在生成抓牌或出牌事件时确定至少存在一个可响应操作
- **THEN** 服务端 MUST 生成 `appearanceResolution` 为 `await-response` 的抓牌或出牌事件
- **AND** 事件 MUST NOT 公开可响应玩家、动作类型或其他私密规则计算结果

#### Scenario: 所有响应玩家后来选择过
- **WHEN** 出现牌事件最初存在响应机会但所有响应玩家后来均选择“过”或被托管过牌
- **THEN** 服务端 MUST 生成将当前保留出现牌归入弃牌区的最终归位事件
- **AND** 服务端 MUST 在最终归位事件动画完成后才继续下一次牌局推进
- **AND** 服务端 MUST NOT 为各个过牌选择分别生成公开 `pass` 事件

#### Scenario: 凑牌生成公开事件
- **WHEN** 玩家通过吃、碰、招或踏完成一手公开凑牌
- **THEN** 服务端 MUST 生成包含动作类型、行动席位、来源席位、稳定 meld id 和最终公开牌组的事件
- **AND** 事件 MUST 足以让客户端构建完整牌组并移动到对应玩家凑牌区

#### Scenario: 结果生成公开事件
- **WHEN** 牌局发生胡牌、进圈、流局或结算
- **THEN** 服务端 MUST 生成对应公开结果事件
- **AND** 结果事件 MUST 位于导致结果的动作事件之后

#### Scenario: 公开事件不泄露暗牌
- **WHEN** 服务端构建公开操作事件
- **THEN** 事件 MUST NOT 包含其他玩家未公开手牌的牌面或 card id
- **AND** 客户端 MUST 仅能从事件读取已公开的牌面与动作信息

### Requirement: 服务端动画推进屏障
服务端权威牌局状态机 SHALL 在每个公开操作事件发布后进入动画等待状态。动画等待状态期间服务端 MUST 暂停后续自动推进和新的牌局操作；只有当前事件要求的在线客户端全部完成动画回执，或未回执客户端达到超时并按掉线托管处理后，服务端才可以继续下一个动作。断线或超时客户端 MUST 从当前事件必需回执名单移除。对于 `await-response` 出现牌事件，入场动画完成并保留等待牌即视为当前事件动画完成；对于 `auto-discard` 出现牌事件，必须在牌移动到弃牌区并完成静态交接后才视为动画完成。响应窗口内的私有过牌选择 MUST NOT 建立新的动画屏障。

#### Scenario: 所有在线客户端回执后继续
- **WHEN** 当前公开事件要求回执的所有在线客户端均提交了对应 `eventSeq` 的动画完成回执
- **THEN** 服务端 MUST 解除动画等待状态
- **AND** 服务端 MUST 继续执行当前事件保存的下一阶段推进

#### Scenario: 动画等待期间拒绝新操作
- **WHEN** 房间仍在等待当前公开事件的动画完成回执
- **THEN** 服务端 MUST 拒绝新的出牌、响应、接庄或其他推进牌局的操作
- **AND** 权威牌局状态 MUST NOT 跳过当前动画节点

#### Scenario: 等待响应出现牌完成后开放响应
- **WHEN** `appearanceResolution` 为 `await-response` 的出现牌事件已在所有必需客户端完成入场动画并保留等待牌
- **THEN** 服务端 MUST 解除当前出现牌事件的动画屏障
- **AND** 服务端 MUST 开放对应并发响应窗口

#### Scenario: 自动归位完成后继续牌局
- **WHEN** `appearanceResolution` 为 `auto-discard` 的出现牌事件已在所有必需客户端完成归位和静态 mini 牌交接
- **THEN** 服务端 MUST 解除当前出现牌事件的动画屏障
- **AND** 服务端 MUST 继续下一玩家摸牌或其他后续推进

#### Scenario: 响应动画完成后继续牌局
- **WHEN** 玩家完成吃、碰、招、踏或胡的最终裁决动作，或响应窗口最终无人响应
- **THEN** 服务端 MUST 发布对应公开事件并等待客户端完成动画
- **AND** 服务端 MUST 在响应动画屏障解除后才进入出牌、摸牌或结算等下一阶段

#### Scenario: 重复回执幂等
- **WHEN** 同一客户端重复提交同一 `eventSeq` 的动画完成回执
- **THEN** 服务端 MUST 只记录一次该客户端回执
- **AND** 后续牌局推进 MUST NOT 被重复执行

#### Scenario: 回执超时解除阻塞
- **WHEN** 必需回执客户端在截止时间内未完成动画回执
- **THEN** 服务端 MUST 将该客户端按掉线或托管策略处理并从必需回执名单移除
- **AND** 剩余条件满足后服务端 MUST 继续牌局

### Requirement: 掉线托管推进边界
服务端权威状态机 SHALL 在玩家掉线或超时后区分自动推进阶段与手动决策阶段。无需玩家选择的自动摸牌、自动弃牌、响应窗口过牌和可安全选择的出牌阶段 MAY 由服务端托管继续推进；接庄选择、送牌以及从手牌中选择出牌等需要本人明确选择且无法安全托管的阶段 MUST 暂停等待该玩家重连。响应窗口内的离线、超时或托管席位 MUST 快速选择托管动作或过牌，不得阻塞其他真人响应。

#### Scenario: 掉线后自动推进到手动节点
- **WHEN** 掉线玩家所在座位后续只需要自动摸牌、无人响应归位、响应窗口过牌或服务端可安全托管出牌
- **THEN** 服务端 MUST 继续推进牌局
- **AND** 牌局 MUST 在下一次需要掉线玩家本人手动选择且无法安全托管的位置暂停

#### Scenario: 响应选择由托管快速处理
- **WHEN** 掉线、超时或托管玩家处于可吃、碰、招、踏、胡或过的响应窗口
- **THEN** 服务端 MUST 使用 AI/托管策略快速提交合法动作或过牌
- **AND** 该席位 MUST NOT 因等待重连而阻塞响应窗口裁决

#### Scenario: 强制响应托管仍遵守规则
- **WHEN** 掉线、超时或托管玩家在响应窗口内存在 forced 动作
- **THEN** 服务端 MUST 按既有 forced 规则处理托管选择
- **AND** 若托管过牌违反 forced 规则，牌局 MUST 按规则结算对应进圈结果

#### Scenario: 接庄和送牌等待重连
- **WHEN** 掉线玩家处于接庄选择或滑庄送牌阶段
- **THEN** 服务端 MUST 保留当前阶段并等待玩家重连
- **AND** 服务端 MUST NOT 自动替该玩家接庄、拒绝接庄或选择送牌
