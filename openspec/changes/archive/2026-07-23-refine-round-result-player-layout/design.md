## Context

当前结果页使用固定玩家条目高度：头像为 `38～64px` 圆形并与昵称、角色标签横向排列，结果牌宽度为 `16～29px`。公开牌组带有“吃、碰、招、踏”标签，而 `finalHand` 仅按 `phraseId` 聚合，没有使用胡牌时已经生成的权威拆门信息。服务端 `result.card` 保存最后胡到的牌，`result.doors` 保存胡牌分组，但 `roundDetail` 目前只把胡牌追加到赢家 `finalHand`，没有单独公开胡牌与分组字段。

这次修改横跨服务端冻结结果、客户端座位旋转、结果页布局和 Canvas 绘制。结果页仍必须支持四家纵向滚动、窄横屏安全区和下一局操作，不改变结算规则。

## Goals / Non-Goals

**Goals:**

- 将结果页 mini 牌的宽高与叠放节奏调整到原视觉尺寸的约 `80%`，同时保持原始比例和真机可辨认性。
- 使用更小的正方形头像，将昵称放在头像下方，释放横向牌型空间。
- 使用服务端权威数据同时展示赢家完整胡牌牌型和独立“胡”牌列。
- 保证“吃上胡”等情况显示为完整的“吃 上大人”，并额外显示“胡 上”，两个“上”都保留。
- 保证 snapshot、delta 和重连后的结果详情一致。

**Non-Goals:**

- 不修改胡牌判断、拆门算法、胡数和分数计算。
- 不调整结果页标题、面板切图、继续按钮、滚动交互或总战绩入口。
- 不为进圈、流局或荒庄创建“胡”牌列。
- 除用户提供的赢家“胡”标记和胡型竖牌背景外，不新增图片资源或改变小游戏分包结构。

## Decisions

### 1. 冻结结果显式携带 `winningCard` 和 `winningGroups`

赢家的 `roundDetail.players[]` 增加 `winningCard` 与 `winningGroups`；非赢家和非胡牌结果保持空值。服务端从已经裁决完成的 `result.card` 和 `result.doors` 构造这些字段，并把门中的 key 映射回冻结牌对象。

`finalHand` 继续包含最后胡到的牌，确保它仍参与完整胡牌分组。`winningCard` 是用于说明“最后胡哪张”的第二份显示语义，渲染时不得从完整牌型中删除或去重。

选择服务端冻结分组而不是让客户端根据 `finalHand` 重算，是为了避免重复牌、对子挂载以及多种合法拆门造成客户端展示与实际计分拆门不一致。

### 2. 赢家使用权威分组，其他玩家保持现有展示语义

胡牌赢家优先按 `winningGroups` 绘制完整牌型，每组带“吃、碰、对”等权威标签；公开的招、踏等操作牌组继续保持其动作标签。其他玩家没有胡牌拆门，继续使用现有 `melds + finalHand phraseId` 分列方式。

独立“胡”列追加在赢家完整牌型之后、胡数和本局分数之前。其标签固定为“胡”，牌面使用 `winningCard`。该列不占用非赢家的固定空白。

### 3. 牌尺寸使用相对缩放并设置可辨认下限

结果牌目标宽高为原计算结果的约 `0.8` 倍，实际宽度控制在约 `13～23px`，纵向 step 与列间距同步缩放。布局仍根据可用宽度限制最大值，并设置面向最窄支持横屏的最小宽度，避免在低分辨率设备上不可辨认。

牌组整体在玩家条目的可用高度内对齐，不通过恢复横向单列来换取空间。新增“胡”列参与总列宽计算，必要时使用已经存在的结果列表纵向滚动，而不覆盖统计区域。

### 4. 身份区改为纵向信息栈

头像保持 1:1，改用小圆角矩形裁切，不再使用半径等于宽度一半的圆形裁切。头像尺寸缩小，并在身份区内水平居中；昵称放在头像下方居中截断。本家或胡牌身份标签放在昵称下方或头像边角，不再占用头像右侧宽度。

身份区宽度相应缩小，释放的空间分配给牌型区域。玩家条目高度和整页纵向滚动模型保持不变。

### 5. 在线座位旋转只旋转 seat，不改变牌与分组内容

`rotateRoundDetail` 继续旋转玩家 seat，并浅复制 `winningCard`、`winningGroups` 及其 cards。牌对象没有座位坐标，不进行额外变换。snapshot 与 delta 均使用相同映射路径。

### 6. 单列最多五张并按同字门子边界分列

渲染器在完成公开牌组、普通 `phraseId` 分组或权威 `winningGroups` 选择后，对每个待绘制列执行统一的最大高度处理。5 张及以下原样保留；超过 5 张时，先按牌序识别连续相同 key 的门子。3～5 张的同字门子作为不可跨越的独立列；少于 3 张的相邻片段可在不超过 5 张的前提下合并；单一同字片段自身超过 5 张时，再均衡拆成多个不超过 5 张的列。

该策略让“上上上大大人”显示为“上上上”和“大大人”，让“尔尔尔小小小小”显示为“尔尔尔”和“小小小小”，避免把不同同字门子错误切成“尔尔尔小”和“小小小”。带动作标签的原列只在第一段保留标签，后续段视为同一分组的延续；独立“胡”列不参与合并。

### 7. 结果标签按动作类型和同字门子张数解析

公开牌组优先使用权威 `meldType/type`：`zhao` 显示“招”，`ta` 显示“踏”，`peng` 显示“碰”。暗牌拆门统一使用 `same` 类型时，再按门内张数区分：3 张显示“碰”，4～6 张显示“招”。二牌门按门类型区分：`xx` 是两张相同牌，显示“对”；`xy` 是同句两张不同牌，显示“口”。客户端采用相同规则覆盖旧服务端可能下发的错误标签，保证首次结果、增量同步和重连回退一致。

### 8. 赢家牌列右侧使用胡标记和胡型竖牌

服务端在赢家 `roundDetail` 冻结 `huGrade`，取权威 `result.grade`，缺失时回退 `result.scoring.grade`。客户端优先读取赢家详情的 `huGrade`；字段为空时回退公共权威 `state.result.grade` 或 `state.result.scoring.grade`，以兼容滚动部署和升级前已冻结的结果。客户端只做展示名称归一化：`屁胡/平胡 → 平胡`、`小甲 → 小甲`、`大甲 → 大甲`、`场/场胡 → 场胡`，四种结果均为两个汉字。

赢家完整牌型和独立胡牌牌面绘制完成后，在牌区最右侧预留固定装饰区：先绘制金色“胡”PNG，再绘制金红竖牌背景，并将胡型两个字由上到下居中绘制。非赢家不预留该空间。资源从用户提供的 RGBA PNG 裁掉透明留白并按实际显示密度缩放为 `192×192` 和 `120×240`，继续保留 Alpha，将合计包体增量控制在约 90KB。

## Risks / Trade-offs

- [牌面过小会导致真机难辨认，过大又会挤压胡牌列] → 采用约 `80%` 的折中尺寸和 `13～23px` 宽度边界，并在最窄支持横屏尺寸加入布局检查。
- [最后胡牌在完整牌型和“胡”列出现两次可能被误判为数据重复] → 在字段、测试和绘制接口中明确这是有意的双重展示语义。
- [门的 key 映射到实际重复牌时可能选择错误 copy] → 服务端按门顺序从冻结牌池逐张消费，使用卡牌 id 保证每个完整分组内部不重复占用；独立 `winningCard` 允许再次引用同一 id。
- [旧客户端不识别新增字段] → 字段为向后兼容的附加字段，旧客户端仍按 `finalHand` 和 `melds` 展示；新客户端在字段缺失时退回当前结果布局且不伪造“胡”列。
- [新客户端连接未更新服务端时缺少胡牌列] → 先部署后端，再上传小游戏版本；回滚客户端不会影响服务端既有字段。
- [拆分长列可能增加横向列数] → 使用达到每列最多 5 张所需的最少列数，并复用已经释放的身份区宽度；多尺寸检查确保统计区不被覆盖。
- [通用 `same` 类型丢失招的动作语义] → 服务端按张数生成权威标签，客户端再以类型和张数兼容校正；明确的 `ta` 始终优先显示“踏”。
- [`xx` 与 `xy` 都被映射为“对”而丢失口门语义] → 服务端和客户端分别固定映射 `xx: 对`、`xy: 口`，并用“上上 / 上大”对照回归。
- [赢家装饰挤压牌列或统计区] → 只在赢家牌区内部预留固定宽度，按行高约束胡标记和竖牌尺寸，并继续通过多横屏尺寸检查确保不越过统计区。
- [原始 PNG 合计接近 1.8MB] → 裁除透明留白、按显示密度降采样且保留 Alpha，资源合计约 90KB。
- [客户端已更新但结果详情尚未携带 `huGrade`] → 仅赢家行回退读取同一公共结果中的权威 `result.grade`，非赢家不得继承该值。

## Migration Plan

1. 服务端扩展 `roundDetail` 并补充后端与在线同步回归。
2. 客户端扩展座位旋转和结果页绘制，保留缺字段回退路径。
3. 运行胡牌、在线、服务端核心和后端完整检查。
4. 先部署后端并确认健康检查，再上传新的小游戏开发版本进行真机验证。
5. 如需回滚，客户端可恢复旧绘制逻辑；服务端新增字段对旧客户端无副作用。

## Open Questions

无。按用户确认的语义，完整牌型与独立胡牌列有意重复显示最后胡到的牌。
