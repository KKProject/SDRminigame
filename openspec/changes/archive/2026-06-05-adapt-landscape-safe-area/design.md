## Context

当前游戏横屏运行，`render.js` 负责读取微信窗口信息并建立 canvas 逻辑尺寸/高分屏 backing store，`layout.js` 基于逻辑宽高计算头像、手牌、弃牌、凑牌、弹窗和动画终点，`renderer.js` 将背景全屏绘制后按布局区域绘制元素。

全面屏设备在横屏时可能在左侧或右侧存在不可用区域。背景可以继续铺满，因为遮挡背景不影响操作；但头像、文字、牌、按钮和动画终点如果进入遮挡区域，会导致内容不可见或无法点击。

## Goals / Non-Goals

**Goals:**

- 背景图继续覆盖整个 canvas，不因安全区缩小背景。
- 所有可读、可点击、需要观察的游戏元素进入安全内容区域。
- 支持横屏左/右不同遮挡方向，适配 iPhone 刘海、灵动岛、圆角和 Home Indicator。
- 在微信安全区信息不可用时继续使用保守边距，保证旧设备正常运行。
- 自动检查覆盖有明显左右安全边距的横屏设备。

**Non-Goals:**

- 不新增真实头像资源或美术资源。
- 不改变当前横屏方向配置、牌局规则、发牌逻辑或素材 atlas 命名。
- 不为背景添加裁剪、缩放策略或额外遮罩。
- 不处理浏览器 DOM 的 CSS `safe-area-inset-*`，本项目主要运行在微信小游戏 canvas 环境。

## Decisions

### 决策 1：渲染尺寸保持全屏，布局新增安全内容矩形

背景仍然使用 `layout.width` 和 `layout.height` 全屏绘制。`render.js` 或布局入口提供 `safeAreaInsets`，`layout.js` 计算 `contentBounds = { x, y, width, height }`，所有元素布局基于这个安全内容矩形进行 clamp 和居中。

理由：背景被刘海或圆角遮挡不影响玩法，元素被遮挡才是问题。分离“背景全屏”和“内容安全区”可以保持当前视觉效果，同时降低对渲染器的侵入。

备选：直接把 canvas 逻辑尺寸缩小到安全区。该方案会让背景不再全面，且触摸坐标、动画起点和已有测试都需要大幅调整，因此不采用。

### 决策 2：优先读取 `wx.getWindowInfo().safeArea`

微信小游戏运行时若提供 `safeArea`，可通过 `left/top/right/bottom` 与逻辑窗口宽高计算四边 inset。优先读取该数据；若缺失或异常，则使用当前布局已有的 `safe` 常量作为兜底。

理由：`safeArea` 是微信侧对具体设备遮挡区域的运行时描述，能覆盖横屏左/右方向差异。兜底可以保护开发者工具、旧基础库或测试环境。

备选：写死 iPhone 型号边距。该方案不可维护，也无法覆盖安卓全面屏和未来设备，因此不采用。

### 决策 3：布局函数接受安全区输入而不是在布局内部调用 `wx`

`render.js` 负责与微信运行时交互并导出安全边距，`TableLayout` 构造或 `build` 时使用这些边距。测试可直接传入模拟安全区。

理由：布局应保持纯计算，便于自动测试不同屏幕与安全区组合。微信 API 调用集中在 runtime 层也更符合现有结构。

备选：`layout.js` 内部直接调用 `wx.getWindowInfo()`。该方案让布局难测，并增加非微信环境的兜底复杂度，因此不采用。

### 决策 4：触摸命中跟随安全区后的布局区域

`TableLayout.hit` 不需要单独理解安全区，只要 `handCards`、`actionButtons`、`muteButton` 等区域已经避开遮挡即可。输入层继续使用当前布局区域命中。

理由：避免在输入层重复做坐标修正，减少交互 bug。

## Risks / Trade-offs

- [Risk] 安全区过大时可用宽度减少，手牌列可能变窄。→ 通过现有牌尺寸计算和最小宽度约束保持可点击，并在测试中覆盖极端左右 inset。
- [Risk] 开发者工具或旧基础库返回的 `safeArea` 字段不完整。→ 对字段进行数值校验，异常时回退到默认 safe。
- [Risk] 横屏方向旋转后左右 inset 变化但布局未更新。→ 每次布局构建使用最新导出的安全区数据，必要时 `render.js` 在窗口信息变化后更新全局安全区。
- [Risk] 背景全屏但内容缩进后视觉上两侧留空。→ 这是预期效果；背景仍然可见，内容不被遮挡优先。
