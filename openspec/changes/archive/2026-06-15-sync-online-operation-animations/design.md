## Context

在线牌桌当前以 `roomStates` 文档为实时同步入口。服务端每次合法操作完成后，把最终公共快照写入该文档；客户端 `watch` 到变化后再调用 `pull`，将最新快照直接写入本地 `databus`。服务端权威引擎会在一次云函数调用内同步推进 AI 决策、摸牌、无人响应和后续动作，因此一次写入可能跨过多个对玩家可见的牌局步骤。

现有渲染器能根据 `drawnCard`、`recentDiscard`、凑牌区和结果状态播放动画，但它只能观察客户端实际收到的快照。被服务端在同一次推进中覆盖掉的中间状态无法由客户端可靠恢复，也不能由客户端自行推断，否则会破坏服务端权威和规则一致性。

## Goals / Non-Goals

**Goals:**

- 让在线模式下所有玩家的公开摸牌、出牌、响应、凑牌和结算过程在每个客户端按真实顺序可见。
- 保持服务端为唯一权威来源，客户端只消费服务端明确记录的公开事件。
- 服务端在每个公开动作动画完成前暂停推进，防止连续事件重叠、跳步或漏播。
- 支持断线重连、事件缺失、重复回执和动画回执超时后的可靠恢复。
- 保持其他玩家手牌和不可公开信息的隐私边界。

**Non-Goals:**

- 不实现完整对局回放、永久事件日志或观战系统。
- 不改变花牌规则、操作优先级、计分或现有动画视觉风格。
- 不向其他玩家公开其本不应知道的暗牌或手牌内容。

## Decisions

### 决策 1：使用“权威快照 + 单步公开事件 + 动画屏障”

服务端每次只推进到下一个可见动作节点，生成一个公开事件并写入对应权威快照。事件包含全局连续 `eventSeq`、事件类型、行动席位、来源席位、公开牌、公开动作、目标区域、关联牌组和必要提示。`roomStates` 保存当前事件、最新事件序号、动画等待状态和最近少量已完成事件。

服务端发布事件后进入 `awaiting-animation-ack` 状态，暂停 AI、自动摸牌、无人响应处理和后续阶段推进。所有当前在线真人客户端完成动画并回执当前 `eventSeq` 后，服务端解除屏障并继续到下一个动作节点。

不选择“服务端连续推进后客户端补播事件批次”，因为这不能满足玩家看到动作后服务端才继续的节奏要求。也不选择“客户端比较前后快照推断动作”，因为复杂连续操作会产生歧义并可能泄露规则推断。

### 决策 2：事件由服务端权威引擎显式产生

服务端引擎在公开动作完成的位置调用统一事件记录器，例如：

- `draw`：公开摸牌进入玩家前方。
- `discard`：玩家出牌并进入等待响应位置。
- `unclaimed`：牌无人响应，移动到弃牌区。
- `chi`、`peng`、`zhao`、`ta`：响应牌和公开凑牌信息移动到目标玩家凑牌区。
- `pass`、`takeover`、`declineTakeover`：显示动作反馈。
- `hu`、`circleLoss`、`drawRound`、`settlement`：播放结果反馈并进入最终状态。

事件只记录服务端已经裁决完成的事实，不接受客户端生成或修改。只有公开牌面可以进入事件载荷；其他玩家手牌来源只允许用“从该玩家手牌区域移出若干张背面牌”之类的非敏感表现描述，不能包含暗牌明细。

### 决策 3：客户端播放当前事件并发送幂等动画回执

`OnlineController` 维护：

- `lastConsumedEventSeq`：最后已完成播放的事件序号。
- `activeEvent`：当前服务端要求展示的唯一事件。
- `isAnimatingRemoteEvent`：是否正在播放当前在线事件。
- `lastAckedEventSeq`：最后已成功回执的事件序号。

客户端收到实时状态后先去重并播放当前事件。渲染器通过明确的“开始事件动画 / 动画完成”接口消费事件，不再仅依赖当前快照字段碰巧变化来发现在线动作。动画完成后客户端调用 `ackAnimation(eventSeq)`；该接口 MUST 幂等，重复回执不得重复推进。

本人操作也以服务端确认事件为准，避免本地动画和服务端动画重复；本地点击反馈可以立即显示，但牌局动作动画必须等待权威事件。

### 决策 4：服务端保存等待名单、回执集合和继续令牌

每个待播放事件保存：

- `eventSeq` 与当前公开事件。
- 发布事件时在线真人玩家的 `requiredAckOpenids`。
- 已完成动画的 `ackedOpenids`。
- `ackDeadlineAt`。
- 动画结束后继续执行的服务端阶段或继续令牌。

服务端只有在所有必需回执到齐后才执行继续令牌。掉线、超过截止时间或已进入托管的玩家从必需回执名单中移除；超时解除后服务端继续牌局，并在公共状态中显示该玩家已掉线或托管。

### 决策 5：动画期间锁定新的牌局动作

当房间处于 `awaiting-animation-ack` 时，服务端 MUST 拒绝新的出牌、响应和接庄意图，避免动画未完成时状态再次推进。客户端也 MUST 暂停操作输入，只保留当前动画与必要状态提示。动画屏障解除后，服务端才发布下一操作机会。

### 决策 6：缺口、重复与断线采用快照恢复

- `eventSeq` 小于等于 `lastConsumedEventSeq`：视为重复，忽略。
- 收到序号存在缺口：立即 `pull` 最新快照与当前待确认事件。
- 首次进入或断线重连时若房间正在等待当前客户端回执，客户端 MUST 播放当前事件后回执；若该客户端已被服务端移出等待名单，则直接对齐最新快照。
- 客户端回执失败时重试同一 `eventSeq`，服务端按幂等方式处理。

### 决策 7：事件记录有界且不进入永久历史

`roomStates` 以当前待确认事件为主，只保留最近少量已完成事件用于诊断和断线校验。权威 `rooms` 文档保留最新 `eventSeq`、动画屏障和继续令牌，避免云函数重载后序号倒退或丢失待继续阶段。

## Risks / Trade-offs

- [任一客户端不回执导致整桌阻塞] → 设置动画回执截止时间；超时客户端标记掉线或托管并从等待名单移除。
- [动画屏障增加云函数调用与数据库写入] → 回执幂等、只在最后一个必需回执到达时继续推进，并限制已完成事件历史。
- [事件字段意外泄露他人手牌] → 事件构建集中在服务端公开事件序列化器，并增加隐私自动化测试。
- [多客户端动画耗时不一致] → 服务端等待所有当前在线客户端完成；较慢客户端不影响动画正确性，但受统一超时上限约束。
- [旧房间没有事件字段] → 客户端兼容无事件快照，直接渲染；服务端首次写入时初始化事件序号。
- [继续令牌持久化错误导致重复推进] → 每个屏障使用事件序号与房间版本做幂等校验，继续动作只能执行一次。

## Migration Plan

1. 服务端引擎增加公开事件记录器、动画屏障和继续令牌，但先保持动画回执开关关闭。
2. 客户端上线当前事件播放与 `ackAnimation` 回执，兼容没有动画屏障字段的旧房间。
3. 内部灰度开启服务端动画屏障，验证超时解除和掉线托管。
4. 真机验证四席连续摸牌、出牌、吃碰招踏、过、胡和结算均在回执后继续。
5. 观察动画回执耗时、超时率和云函数调用量，再确定最终截止时间。

回滚时关闭服务端动画屏障，恢复直接推进和快照渲染；事件字段可继续保留，不影响旧客户端。

## Open Questions

- 动画回执截止时间采用固定值还是按动作类型区分，需要通过真机网络测试确定。
- 其他玩家“吃”牌时，是否需要表现其两张上手牌的具体正面；若这些牌在吃完成前不属于公开信息，则动画仅在凑牌区展示最终公开牌组。
- 回执等待范围默认包含所有在线真人玩家；后续如增加观战者，观战者不应进入必需回执名单。
