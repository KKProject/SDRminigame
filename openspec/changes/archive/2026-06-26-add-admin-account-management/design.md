## Context

现有自有后端已经提供 `/admin` 页面和 `/api/admin/status`、`/api/admin/clear` 两个管理 API，但授权方式是单一 `ADMIN_TOKEN`。这个方式不适合长期维护：无法区分管理员、无法从页面新增账号，也不便于后续扩展审计和权限。

后端目前是 Node.js HTTP 服务，数据库层提供统一的文档集合接口，并已支持内存、文件和 MongoDB 三种适配。后台页面由 `services/backend/src/admin-page.js` 直接返回静态 HTML，因此本次改造继续沿用单文件页面，避免引入前端构建链。

## Goals / Non-Goals

**Goals:**
- 让维护者通过 `/admin` 打开网页，使用账号密码登录。
- 提供默认超级管理员与初始化凭据（历史凭据已移除），确保首次部署后可以进入后台。
- 登录后可继续管理房间数据清理功能。
- 超级管理员可以在页面内创建新管理员，并禁用非默认管理员。
- 管理 API 使用会话 token 鉴权，禁用账号后其会话失效。
- 管理员账号保存在后端数据库中，服务启动时自动确保默认超管存在。

**Non-Goals:**
- 不接入第三方 OAuth、短信、邮箱或微信后台登录。
- 不实现复杂 RBAC；本次只区分 `superadmin` 和 `admin`。
- 不新增完整审计日志系统。
- 不把后台拆成独立 Web 应用或引入 Vite/React。

## Decisions

1. **使用数据库集合保存管理员账号**
   - 方案：新增 `adminUsers` 集合，文档 id 使用用户名，字段包含 `username`、`passwordHash`、`salt`、`role`、`enabled`、`createdAt`、`updatedAt`、`createdBy`。
   - 理由：符合用户“后台写入/页面新增管理员”的管理诉求，并能在文件数据库和 MongoDB 中保持一致。
   - 备选：只用环境变量 `ADMIN_USERS_JSON`。缺点是页面新增后无法持久化到同一管理面板，维护成本更高。

2. **默认超管由服务启动时确保存在**
   - 方案：`createBackendServer` 初始化时创建 `AdminService` 并调用 `ensureDefaultAdmin()`。如果 `wangyk` 不存在则写入默认密码；如果已存在则不覆盖。
   - 理由：首次部署即能登录，同时避免覆盖维护者后续手动调整过的账号。
   - 备选：硬编码登录时临时放行默认账号。缺点是无法在管理员列表中统一管理，也无法支持禁用会话逻辑。

3. **密码使用内置 `crypto.pbkdf2` 哈希**
   - 方案：每个账号独立 salt，使用 `pbkdf2Sync` 生成摘要，保存为 `pbkdf2$iterations$salt$hash`。
   - 理由：避免明文密码和外部依赖；对当前小型后台足够可靠。
   - 备选：引入 bcrypt/argon2。安全性更好，但会增加依赖和部署复杂度。

4. **会话 token 使用 HMAC 签名的无状态 token**
   - 方案：登录后签发包含用户名、角色、过期时间和 nonce 的 token，使用 `ADMIN_SESSION_SECRET` 或后端已有 secret 签名。
   - 理由：无需新增 session 存储即可满足后台管理；每次请求仍会读取账号状态，禁用账号后 token 不再有效。
   - 备选：服务端存储 session。优点是可主动注销所有会话，缺点是需要新增集合和更多状态管理。

5. **页面采用“登录面板 + 运维工作台”单页结构**
   - 方案：未登录展示账号密码表单；登录后展示房间集合计数、清理操作、管理员列表和新增管理员表单。
   - 理由：管理者访问频率低，但操作风险高；单页能减少跳转，二次确认能降低误删概率。

## Risks / Trade-offs

- 默认密码公开 → 部署后应尽快创建新的超级管理员或修改数据库中的默认账号密码；页面和 `.env.example` 会明确提示。
- 无状态 token 无法单独吊销某一次登录 → 每次请求都会校验账号启用状态，禁用管理员即可让其后续请求失败。
- `pbkdf2Sync` 是同步计算 → 管理后台请求量极低，可接受；迭代次数控制在不会影响服务响应的范围。
- 旧 `ADMIN_TOKEN` 入口被替换 → 通过测试和文档说明迁移到账号密码登录。

## Migration Plan

1. 部署新版后端并重启。
2. 服务启动时自动确保默认超管 `wangyk` 存在。
3. 维护者访问 `/admin`，使用默认账号登录。
4. 登录后新增自己的管理员账号；如需更高安全性，可后续直接修改数据库中默认超管密码摘要或禁用其它非默认管理员。
5. 回滚时可回到上一版本，旧版仍按 `ADMIN_TOKEN` 运行；新增的 `adminUsers` 集合不会影响游戏数据。
