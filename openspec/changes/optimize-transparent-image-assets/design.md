## Context

`images/` 当前包含 16 张带 alpha 的 PNG，总体积约 2.32 MB。资源既包含独立 UI 图片，也包含由 JSON 坐标裁切的 `actions.png`、`element.png` 等 atlas。现有资源直接通过相对路径加载，因此最小风险方案是在原路径上替换经过验证的 PNG 编码，而不改变运行时逻辑。

## Goals / Non-Goals

**Goals:**

- 对 `images/*.png` 做可重复、确定性的无损优化。
- 保持图片尺寸、解码后的 RGBA 像素和 alpha 数据完全一致。
- 仅接受确实减小体积的输出，并报告逐文件节省量。
- 使用自动化检查保护 atlas 坐标兼容性和透明通道。

**Non-Goals:**

- 本 change 不转换 WebP/AVIF，不改变资源路径。
- 不缩放、裁切或重新打包 atlas。
- 不对 JPG 背景执行有损重编码。
- 不引入运行时图片解码依赖。

## Decisions

1. 使用 Node 内置 `zlib` 对 PNG 已过滤的扫描线做无损 DEFLATE 重压缩，并从多种标准压缩策略中选择最小输出。它不重新量化颜色，也不会改变半透明边缘或像素数据。
2. 将优化流程封装为项目脚本，仅使用固定版本的 `pngjs` 作为独立 RGBA 解码校验器，避免依赖开发者机器上的全局图片工具。
3. 优化前后使用独立校验脚本读取 PNG 结构和解码像素：宽高、alpha 能力及 RGBA 哈希必须一致。atlas 因此无需修改 JSON。
4. 优化输出先写入临时目录，只有通过校验且体积更小时才原子替换源文件。失败或无收益时保留原文件。
5. 报告采用机器可读 JSON 和终端摘要，记录原始大小、优化后大小、节省字节数与校验结论。

## Risks / Trade-offs

- [高强度优化耗时较长] → 图片集合较小，使用固定优化级别，并允许重复执行时快速得到无变化结果。
- [Node zlib 版本升级导致输出字节不同] → 验收依赖解码像素一致和体积不增，而非压缩后二进制哈希。
- [PNG 结构包含特殊 ancillary chunk] → 校验渲染相关属性与 RGBA 像素；优化工具只安全移除非关键元数据。
- [部分已优化图片无进一步收益] → 仅替换更小文件，报告为未改变，不将“所有文件都必须变小”作为成功条件。

## Migration Plan

1. 安装固定版本的开发依赖并新增脚本。
2. 记录当前图片基线，执行批量优化。
3. 校验全部 PNG 的尺寸、alpha 和 RGBA 像素。
4. 运行现有小游戏本地回归。
5. 若需回滚，可通过版本控制恢复 PNG 二进制及相关脚本。

## Open Questions

无。本 change 采用严格无损策略；有损量化或 JPG 优化可在后续 change 单独评估。
