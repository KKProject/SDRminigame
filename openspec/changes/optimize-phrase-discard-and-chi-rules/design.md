## Context

当前 `isLegalDiscard()` 通过 `wouldBreakCompletePhrase()` 判断出牌是否会破坏发牌时锁定的原句数量。这个模型可以保护正好成句的 `xyz`，但对 `xxxyz`、`xxyyz`、`zzzxxy` 这类同句多牌结构过于僵硬，不能表达“先打某张后仍有未来路径保留门子”的牌理。

同时，系统已经记录 `actionHistory` 和 `discardPhraseCounts`，但“玩家出过某 key 后不能再吃该 key”的限制尚未参与响应动作枚举。由于在线对战以云端为权威，云函数和客户端同构 evaluator 必须一起更新。

## Goals / Non-Goals

**Goals:**

- 用同句出牌可达性算法替换发牌锁定原句数的出牌限制。
- 让 `xxyz`、`xxxyz`、`xxyyz`、`zzzxxy` 等典型牌型按讨论后的牌理给出合法出牌集合。
- 阻止玩家吃回自己历史上打出过的 key，并阻止该 key 参与吃式胡牌。
- 保持服务端权威校验、AI 选择和客户端提示一致。

**Non-Goals:**

- 不调整八门胡牌整体分解规则、计福计分规则或动作优先级。
- 不改变云函数 `op` API 入参结构。
- 不处理非吃式胡牌是否应被“出过不胡”限制；本变更仅覆盖 `xy` / `xyz` 吃式门。

## Decisions

### 使用可达性算法判断同句出牌

对候选出牌 key 所在句 `x/y/z`，算法模拟打出该 key 后的剩余 counts，并判断是否仍存在一种合法未来，使该句最终保留至少一个门子。门子集合为：

- `xyz`
- `xxx`
- `yyy`
- `zzz`

未来路径允许提前停止。也就是说，打出当前牌后不要求立即成门，但剩余牌必须仍然包含或可通过继续打牌到达一个保留门子；如果某一步会让所有保门可能性消失，则该步非法。

替代方案：继续沿用 `lockedPhraseTriplets`。放弃原因是它会把发牌时的原句数量固化为硬下限，无法表达 `xxyyz` 可先打 `z` 后停止、`xxxyz` 可走 `yz` 留 `xxx` 等路径。

### 用历史动作判断“出过某 key”

优先从 `seat.history.actionHistory` 中读取 `discard` 和 `auto-discard-draw` 记录来判断某 seat 是否曾打出 key。不能只查 `seat.discards`，因为弃牌可能被别人吃、碰、招后从弃牌区移除。

替代方案：新增独立 `discardedKeys` 集合。短期不需要额外状态；若性能或代码清晰度需要，可在实现中派生缓存，但权威来源仍是历史动作。

### 在响应动作枚举层过滤吃与吃胡

`findAppearingCardActions()` 是胡、踏、招、碰、吃的统一入口。过滤应发生在这里或其下游纯函数中，避免客户端/服务端暴露本不应出现的按钮，再在提交时失败。

`吃胡` 的本次实现口径为：当出现牌来自他人出牌，且该 seat 历史上打出过同 key，则不允许该出现牌在胡牌分解中参与 `xy` 或 `xyz` 门。出现牌若只参与 `xx`、`xxx` 或更高同字门，不属于本变更的“吃胡”范围。

### 同步云端与客户端 evaluator

云端 `cloudfunctions/game/core/evaluator.js` 是权威；客户端 `js/game/evaluator.js` 用于本地提示和自检。两份同构逻辑需要保持一致，避免前端展示可点动作但服务端拒绝。

## Risks / Trade-offs

- [风险] 可达性算法若只按当前 counts 判断，可能忽略历史已经打出的同句牌。 → 将 seat 历史中的同句已出牌 key 纳入路径状态，使“当前候选 + 历史已出”共同决定未来是否仍可保门。
- [风险] 胡牌分解当前不标注出现牌落在哪一门，难以精确识别吃胡。 → 扩展胡牌评估上下文或增加辅助判定，用出现牌 key/phraseId 检查是否存在合法胡分解完全避开吃式门；只有所有可赢分解都依赖吃式门时才禁止。
- [风险] AI 候选过滤若回退到非法牌，会触发进圈或异常体验。 → `chooseDiscard()` 必须优先使用新合法集合；无合法牌时沿用现有进圈逻辑。
- [风险] 旧自检断言“完整原句绝对不能拆”会与新算法冲突。 → 更新自检为牌型路径表，覆盖允许提前停止和后续可达性。
