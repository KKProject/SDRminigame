## Context

当前微信小游戏使用 Canvas 渲染牌桌和牌面，`TableRenderer` 已经有一套单张大牌移动动画：出牌/摸牌从玩家侧移动到玩家前方，待响应牌可停留，再移动到弃牌区或凑牌区。参考文档建议的视觉效果更丰富，包括飞行中缩放、当前牌发光描边、操作大字弹出、动作按钮弹性入场和吃牌组合动画。

这次优化应保留现有状态机和资源体系，不引入 PixiJS 或新的渲染依赖，直接在 Canvas renderer 内增加动画属性和效果层。

## Goals / Non-Goals

**Goals:**

- 让出牌/摸牌飞行动画具有 250ms 到 420ms 的快入慢出节奏，飞行中短暂放大并带轻微阴影。
- 当前正在处理或等待响应的牌显示青蓝色高亮描边和 glow。
- 操作动作产生“吃 / 碰 / 招 / 踏 / 胡 / 过”大字弹出、回弹和淡出特效。
- 动作按钮出现时有弹性缩放，点击时有轻微压缩或变亮反馈。
- 吃牌确认后，待响应牌和两张手牌有可见组合过渡，再归入凑牌 mini 区。
- 动画不会阻塞响应弹窗点击，也不会让弃牌/凑牌 mini 重复显示。

**Non-Goals:**

- 不改变游戏规则、AI 决策、动作优先级或结算逻辑。
- 不新增图片资源、音频资源或第三方动画库。
- 不重做整套 UI 布局和头像/弃牌/凑牌区域。

## Decisions

1. 保持 Canvas renderer 内部实现

使用 `TableRenderer` 内部的动画状态、效果数组和绘制顺序完成优化。卡牌、按钮和文字仍由 Canvas 绘制，避免在微信小游戏环境中混入 DOM/CSS 或新增 PixiJS。

替代方案是引入 PixiJS 或 tween 库。虽然效果管理更成熟，但当前项目体量较小，引入依赖会增加加载和适配成本。

2. 将动画绘制分层

渲染顺序保持背景、桌面元素、手牌/mini、效果层、按钮/弹窗。移动中的大牌和操作大字属于效果层；按钮仍属于 UI 层并保持命中区域独立。这样可以让效果在视觉上突出，同时不挡住可点击弹窗。

3. 用动画参数扩展现有 `createCardAnimation`

保留现有 signature/stage 机制，增加 `scalePeak`、`glow`、`shadow`、`holdGlow` 等参数或从 stage 派生这些参数。飞行进度使用 `easeOutCubic`，缩放使用 `sin(pi * progress)` 形成中段放大。

4. 操作大字使用短生命周期 effect

当动作进入 resolved 状态或 renderer 检测到新 meld/win/pass 事件时，追加一个 text effect。effect 按 600ms 到 900ms 生命周期绘制：0 到 20% 弹出，20 到 60% 回弹，75% 后淡出。

5. 吃牌组合动画优先做“可见过渡”

吃牌后要牌的大牌已能从前方飞到凑牌区；新增的人手两张牌可以从手牌位置向凑牌区附近上移/缩放，三张牌短暂并排后结束。若无法定位被消耗手牌位置，则退化为只播放“吃”字和要牌移动，不影响牌局状态。

## Risks / Trade-offs

- [Risk] 多个动画同时触发导致状态覆盖 → Mitigation: 保留移动动画单通道，文本/按钮效果使用独立数组，移动结束后再清理 mini 隐藏状态。
- [Risk] Canvas 阴影和文字描边影响低端设备性能 → Mitigation: 只对当前动画牌和短生命周期文字启用 shadowBlur，数量保持很小。
- [Risk] 点击反馈依赖输入事件传递 → Mitigation: 优先用 renderer 可见状态实现按钮入场；点击压缩可通过 `TableInput` 记录短暂点击反馈，无法实现时不影响主功能。
- [Risk] 吃牌组合动画难以准确追踪被消耗手牌原始位置 → Mitigation: 使用上一次 layout.handCards 快照查找 card id；找不到则退化为凑牌区过渡。
